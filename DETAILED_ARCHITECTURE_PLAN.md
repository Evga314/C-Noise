# 2. Исходная концепция проекта

Native Noise Accelerator — серверный мод Minecraft, предназначенный для ускорения шумового этапа генерации мира посредством выполнения вычислений на нативном машинном коде.

Вместо того чтобы каждый раз выполнять сложное дерево функций плотности через Java, мод:

1. Получает настоящее дерево функций плотности загруженного измерения.
2. Анализирует его структуру.
3. Переводит поддерживаемые участки в компактную программу.
4. Проверяет корректность программы.
5. Передаёт программу нативному движку.
6. Выполняет вычисления пакетами.
7. Возвращает неподдерживаемые участки в Java.
8. Сравнивает результаты с действующей Java-реализацией.
9. Оставляет нативный путь включённым только после прохождения проверок.

## 2.1. Почему используется именно нативный движок

Java уже выполняет значительную часть вычислений достаточно эффективно благодаря JIT-компиляции.

Поэтому простое переписывание отдельных функций на C само по себе не гарантирует существенного ускорения.

Основная архитектурная идея заключается в устранении нескольких источников накладных расходов:

- повторного обхода Java-объектов дерева;
- большого количества виртуальных вызовов;
- повторной обработки одинаковых выражений;
- переходов между отдельными Java-объектами при вычислении формулы;
- недостаточно эффективной организации вычислений по массивам точек;
- избыточной работы с кэшами и интерполяцией;
- недостаточной специализации некоторых вычислительных операций.

Нативный движок должен обрабатывать подготовленную программу, а не воспроизводить Java-объектную модель.

## 2.2. Что отличает проект от обычной замены Java на C

Проект не пытается реализовать собственную независимую генерацию ландшафта.

Он не должен создавать альтернативный алгоритм генерации мира.

Вместо этого он компилирует существующую формулу, которую уже использует Minecraft.

Это позволяет сохранить:

- изменения датапаков;
- настройки измерений;
- пользовательские функции плотности;
- модификации ванильных функций;
- изменения входных данных;
- поддержку разных конфигураций генерации.

При этом неизвестные компоненты не становятся препятствием для работы всей системы.

Они остаются в Java.

# 3. Цели, требования и критерии успеха

## 3.1. Функциональные требования

### FR-001. Обнаружение деревьев

При загрузке мира мод должен получать деревья функций плотности из маршрутизатора шума каждого измерения.

### FR-002. Компиляция

Каждое поддерживаемое дерево должно переводиться в программу плотности.

### FR-003. Частичная поддержка

Неизвестные узлы должны переводиться в `CALL_JAVA`, а не приводить к отказу от всего дерева.

### FR-004. Проверка программ

Перед выполнением каждая программа должна проходить проверку структуры и операндов.

### FR-005. Нативные вычисления

Движок должен принимать массивы точек и выполнять вычисления пакетно.

### FR-006. Обратные вызовы

Поддержка Java должна осуществляться пакетными запросами.

### FR-007. Побитовая проверка

Результаты нативных вычислений должны сравниваться с реальной Java-реализацией.

### FR-008. Проверка генерации чанков

Система должна сравнивать результаты генерации Java и нативным путём.

### FR-009. Автоматическое отключение

При обнаружении расхождения затронутый компонент должен отключаться.

### FR-010. Отчётность

При загрузке мира должен создаваться подробный отчёт о покрытии и причинах отказа от отдельных компонентов.

### FR-011. Подбор реализаций

Система должна тестировать доступные варианты ядер на конкретной машине и выбирать самый быстрый корректный вариант.

### FR-012. Совместимость

Мод должен работать на серверной стороне и не требовать установки на клиентах.

## 3.3. Критерии успеха проекта

Проект считается технически успешным, если:

1. Нативный движок загружается на всех заявленных целевых платформах.
2. Компилятор корректно обрабатывает все поддерживаемые ванильные типы узлов.
3. Верификатор отклоняет некорректные программы.
4. Нативные ядра проходят тесты точности.
5. Golden Chunks проходят проверку.
6. Частичные Java fallback не нарушают корректность программы.
7. Параллельная генерация чанков не вызывает повреждения состояния.
8. Отчёты позволяют определить причину отключения каждого компонента.
9. На реальных нагрузках измеряется положительное ускорение.
10. Ускорение не достигается за счёт изменения генерации мира.

**Важно:** высокая доля нативного покрытия сама по себе не является критерием успеха. Более низкое покрытие с корректными вычислениями предпочтительнее полного покрытия с ошибками.

# 5. Общая архитектура

Проект рекомендуется разделить на независимые слои.

## 5.1. Слой интеграции Minecraft

Обязанности:

- обнаружение загрузки мира;
- получение маршрутизаторов шума;
- получение деревьев функций плотности;
- обнаружение соответствующей стадии генерации;
- передача входных данных компилятору;
- подключение нативного вычисления;
- управление жизненным циклом мира.

Этот слой не должен содержать математическую реализацию нативных ядер.

## 5.2. Слой компиляции Java

Обязанности:

- обход деревьев;
- распознавание типов узлов;
- вызов обработчиков;
- создание инструкций;
- управление таблицами констант;
- оптимизация;
- построение подписей программ;
- обработка неподдерживаемых узлов.

## 5.3. Слой верификации Java

Обязанности:

- проверка структуры программы;
- генерация тестовых векторов;
- сравнение результатов;
- проверка Golden Chunks;
- управление probation;
- локализация ошибок;
- управление отключениями.

## 5.4. Слой взаимодействия с нативным кодом

Обязанности:

- загрузка библиотек;
- проверка ABI;
- выделение и управление буферами;
- вызовы через FFM;
- проверка статусов;
- обработка пакетных обратных вызовов.

## 5.5. Слой нативного движка

Обязанности:

- выполнение байткода;
- вызов листовых ядер;
- обработка массивов;
- интерполяция;
- обработка `CALL_JAVA`;
- возврат результатов.

## 5.6. Слой выбора производительности

Обязанности:

- обнаружение доступных возможностей процессора;
- проверка вариантов ядер;
- проведение бенчмарков;
- выбор вариантов;
- кэширование результатов;
- формирование таблицы подбора.

## 5.7. Слой диагностики

Обязанности:

- структурированные логи;
- отчёты покрытия;
- статистика времени;
- сведения о несовпадениях;
- информация о выбранных ядрах;
- экспорт диагностических данных.

## 5.8. Запреты на смешивание обязанностей

Не рекомендуется:

- размещать обработчики Minecraft непосредственно в C;
- выполнять обход Java-дерева из нативного кода;
- хранить изменяемое состояние мира в глобальных переменных C;
- вызывать произвольные Java-методы из каждого листового ядра;
- смешивать бенчмарки с обычной генерацией;
- помещать правила совместимости модов внутрь математических ядер;
- разрешать внешним обработчикам изменять внутреннюю память движка.

# 6. Полный жизненный цикл ускорителя

## 6.1. Запуск игры

При запуске:

1. Загрузчик обнаруживает мод.
2. Мод проверяет конфигурацию.
3. Определяет доступный механизм взаимодействия с нативным кодом.
4. Определяет операционную систему и архитектуру.
5. Выбирает подходящую библиотеку.
6. Извлекает библиотеку.
7. Загружает её.
8. Проверяет экспортируемые символы.
9. Проверяет версию ABI.
10. Инициализирует Java-обёртку.
11. Регистрирует обработчики.
12. Проверяет конфликты с другими компиляторами.

Если загрузка библиотеки не удалась, мод должен перейти в режим Java-only.

## 6.2. Загрузка мира

При входе в мир:

1. Получить идентификатор мира.
2. Получить конфигурацию генерации.
3. Обнаружить измерения.
4. Получить маршрутизаторы шума.
5. Извлечь корневые деревья.
6. Создать контексты компиляции.
7. Построить подписи деревьев.
8. Проверить кэш программ.
9. При необходимости скомпилировать деревья.
10. Проверить программы.
11. Проверить доступность обработчиков.
12. Выполнить модульные тесты.
13. Выполнить проверку Golden Chunks.
14. Определить допустимые нативные ветви.
15. Сформировать отчёт покрытия.
16. Включить разрешённые нативные пути.

## 6.3. Генерация чанка

При поступлении очередной задачи генерации:

1. Vanilla pipeline достигает стадии шумового заполнения.
2. Интеграционный слой получает контекст вычислений.
3. Определяется соответствующая программа плотности.
4. Формируется пакет координат.
5. Проверяется состояние ускорителя для данного дерева.
6. Вызывается нативный движок.
7. Выполняются поддерживаемые операции.
8. При необходимости собираются запросы `CALL_JAVA`.
9. Java обрабатывает запросы.
10. Движок продолжает выполнение.
11. Результаты возвращаются вызывающему коду.
12. При необходимости выполняется probation-проверка.
13. Данные передаются в дальнейший ванильный pipeline.

## 6.4. Выход из мира

При завершении сессии:

- прекращается использование программ мира;
- освобождаются Java-буферы;
- закрываются выделенные FFM-ресурсы;
- очищаются временные таблицы;
- сохраняются допустимые кэшируемые результаты подбора ядер;
- закрываются диагностические потоки, если они были созданы Java-стороной.

Нативный движок не должен самостоятельно управлять жизненным циклом потоков генерации.

# 7. Архитектура Java Runtime

Рекомендуемое логическое разделение:

```text
runtime/
    bootstrap/
    platform/
    minecraft/
    compiler/
    handlers/
    optimizer/
    bytecode/
    verifier/
    verification/
    fallback/
    bridge/
    memory/
    kernel/
    benchmark/
    reporting/
    config/
    compatibility/
    diagnostics/
```

## 7.1. Bootstrap

Запускает подсистемы в правильной последовательности.

Обязанности:

- регистрация загрузчика;
- чтение конфигурации;
- загрузка native library;
- проверка ABI;
- инициализация реестра;
- обнаружение конфликтов;
- создание глобального состояния ускорителя.

Bootstrap не должен начинать тяжёлые бенчмарки в критическом пути загрузки игры.

## 7.2. Platform

Содержит:

- определение ОС;
- определение архитектуры;
- проверку базовых возможностей процессора;
- выбор файла библиотеки;
- определение доступности FFM;
- платформенные ограничения.

Платформенный слой определяет, какие механизмы доступны, но не должен определять математическую корректность ядра по фиксированной таблице процессоров.

## 7.3. WorldRuntime

Представляет состояние ускорителя для конкретного мира.

Рекомендуемые данные:

```text
WorldRuntime
    worldSignature
    worldSeedFingerprint
    dimensionStates[]
    compiledPrograms[]
    verificationResults[]
    disableRegistry
    kernelSelectionReference
    coverageReport
```

Все эти структуры принадлежат конкретной сессии мира.

## 7.4. DimensionRuntime

Для каждого измерения:

```text
DimensionRuntime
    dimensionIdentifier
    noiseRouterFingerprint
    densityTreePrograms[]
    treeVerificationStates[]
    coverageStatistics
    runtimeStatistics
```

Разные измерения могут иметь разные наборы программ и разные результаты верификации.

## 7.5. ProgramRuntime

Представляет скомпилированную программу:

- ссылку на неизменяемый байткод;
- таблицы констант;
- таблицы сэмплеров;
- версии обработчиков;
- подпись программы;
- результат статической проверки;
- состояние допуска;
- ссылки на используемые ядра.

Программа после публикации для рабочих потоков должна оставаться неизменяемой.

# 8. Извлечение и компиляция деревьев плотности

## 8.1. Источник истины

Компилятор должен работать с реальными объектами загруженной Minecraft-системы.

Нельзя создавать отдельную вручную поддерживаемую модель ванильного дерева, которая может разойтись с настоящей реализацией.

Для каждой версии Minecraft необходимо определить:

- способ получения маршрутизатора шума;
- доступные корневые функции;
- типы внутренних узлов;
- способы получения параметров;
- устройство сэмплеров;
- правила кэширования;
- правила интерполяции;
- особенности контекстных вычислений.

## 8.2. Обход дерева

Рекомендуемый алгоритм:

1. Получить корневой объект.
2. Проверить, был ли объект уже посещён.
3. Определить его тип.
4. Найти обработчик.
5. Получить дочерние объекты.
6. Рекурсивно или итеративно обработать их.
7. Создать внутреннее представление узла.
8. Сохранить соответствие исходного узла и скомпилированного участка.
9. После обхода создать корневую программу.

### Важный момент: граф, а не обязательно дерево

В Java несколько узлов могут ссылаться на один и тот же объект.

Поэтому компилятор должен учитывать повторное использование объектов.

Рекомендуется поддерживать:

- таблицу идентичности исходных объектов;
- таблицу уже обработанных узлов;
- отдельный идентификатор скомпилированного узла;
- безопасное обнаружение циклических ссылок, если они возможны в рассматриваемой реализации.

Нельзя безусловно превращать каждое повторное обращение к одному объекту в отдельную независимую реализацию.

Это может уничтожить общие подвыражения и изменить семантику кэширования.

## 8.3. Внутреннее представление

До генерации байткода рекомендуется построить промежуточное представление — IR.

Пример:

```text
NodeIR
    nodeId
    originalJavaNode
    handlerId
    handlerVersion
    nodeType
    constants[]
    children[]
    purity
    cacheBehavior
    contextRequirements
    compilationStatus
```

`purity` обозначает, является ли вычисление чистой операцией без побочных эффектов.

`contextRequirements` описывает необходимые координаты, контекст ячейки, параметры сэмплера и другие входные данные.

IR позволяет отделить обход Java-объектов от последующей оптимизации.

## 8.4. Группы узлов

Рекомендуется классифицировать узлы следующим образом:

| Категория | Обработка |
|---|---|
| Константы | Таблица констант |
| Простая арифметика | Инструкции VM |
| Ограничение диапазона | Инструкция VM или ядро |
| Перлинский шум | Листовое ядро |
| BlendedNoise | Листовое ядро |
| Сплайны | Инструкция или ядро |
| Кэш-обёртки | Специальные операции |
| Интерполяция | Специальный исполнитель |
| Неизвестные узлы | CALL_JAVA |
| Неподдерживаемые контекстные операции | CALL_JAVA |

## 8.5. Ошибки компиляции

Компилятор должен различать:

- неизвестный тип;
- известный, но неподдерживаемый вариант узла;
- некорректные параметры;
- невозможность извлечь константы;
- превышение лимита сложности;
- циклическую зависимость;
- ошибку генерации инструкции;
- внутреннюю ошибку компилятора.

Для каждого случая необходимо возвращать структурированную причину.

Если возможно, ошибку следует локализовать до поддерева.

## 8.6. Подписи деревьев

Подпись дерева должна зависеть от:

- типа узла;
- его констант;
- порядка дочерних узлов;
- структуры графа;
- версии обработчика;
- версии семантики компилятора;
- используемых специальных операций.

Для числовых констант рекомендуется использовать стабильное представление битов, а не локализованное строковое представление числа.

Подпись не должна включать случайные адреса Java-объектов.

Отдельно следует хранить подпись контекста мира.

Это позволяет отличать:

- идентичность математической структуры;
- идентичность её окружения;
- идентичность конкретного набора данных сэмплера.

# 9. Система обработчиков (Handler Registry)

## 9.1. Назначение

Handler Registry — основной механизм расширения компилятора.

Каждый обработчик отвечает за конкретный тип узла или сэмплера.

Он должен:

1. Распознавать допустимый тип.
2. Извлекать параметры.
3. Извлекать дочерние элементы.
4. Определять контекстные требования.
5. Создавать IR или инструкции.
6. Обеспечивать тестовые векторы.
7. Предоставлять версию семантики.

## 9.2. Логический контракт обработчика

Предлагаемый интерфейс:

```java
interface DensityNodeHandler<T> {

    boolean supports(Object node);

    NodeDescriptor describe(T node);

    void compile(
        T node,
        CompilationContext context,
        ProgramBuilder builder
    );

    VerificationVectors verificationVectors();

    HandlerVersion version();
}
```

Это пример структуры, а не требование использовать именно такие имена методов.

## 9.3. NodeDescriptor

Дескриптор должен содержать:

- идентификатор типа;
- параметры;
- дочерние узлы;
- признаки чистоты;
- сведения о кэшировании;
- сведения о координатной зависимости;
- сведения о контекстной зависимости;
- оценку стоимости;
- версию семантики.

Оценка стоимости может использоваться для отчётности и оптимизации.

## 9.4. Регистрация

Обработчики регистрируются через внутренний интерфейс интеграции (раздел 25.6), а не через точки входа конкретного загрузчика.

Необходимо определить:

- момент регистрации;
- порядок регистрации;
- поведение при дублировании;
- приоритеты;
- изоляцию версий Minecraft;
- правила конфликта двух обработчиков одного типа.

Дублирующиеся регистрации не должны приводить к случайному выбору обработчика.

Рекомендуется завершать регистрацию с диагностической ошибкой либо применять заранее установленное детерминированное правило.

## 9.5. Версионирование

Каждый обработчик должен иметь:

- стабильный идентификатор;
- версию API;
- версию семантики;
- диапазон поддерживаемых версий Minecraft.

Изменение математического поведения обработчика требует изменения его версии семантики.

## 9.6. Внешние обработчики

Внешний мод должен иметь возможность:

1. Объявить зависимость от публичного API.
2. Зарегистрировать обработчик.
3. Предоставить тестовые векторы.
4. Проверить его на публичном верификационном стенде.
5. Получить подробный результат.
6. Исправить несовпадения без изменения ядра движка.

Внешний обработчик не должен иметь прямого доступа к произвольной памяти нативного движка.

# 10. Архитектура программы плотности

## 10.1. Общая модель

Результат компиляции — неизменяемая программа, которую можно исполнять на множестве пакетов координат.

Программа состоит из:

```text
DensityProgram
    Header
    Instructions
    NumericConstants
    SplineConstants
    SamplerDescriptors
    CacheDescriptors
    CallbackDescriptors
    ProgramMetadata
```

## 10.2. Header

Заголовок рекомендуется снабдить:

- версией формата программы;
- версией набора инструкций;
- количеством инструкций;
- количеством констант;
- количеством сэмплеров;
- количеством callback-описаний;
- максимальной глубиной стека;
- ожидаемым числом выходов;
- контрольной суммой содержимого.

Все размеры должны проверяться до передачи в C.

## 10.3. Instructions

Инструкции должны иметь компактное представление.

Возможные форматы:

- фиксированный размер инструкции;
- opcode + индекс операнда;
- opcode + несколько операндов;
- отдельные таблицы аргументов.

Формат выбирается после измерения размера программы и скорости декодирования.

## 10.4. Таблицы констант

Отдельно хранятся:

- значения double;
- параметры шумовых сэмплеров;
- таблицы сплайнов;
- таблицы перестановок;
- описания кэшей;
- описания обратных вызовов.

Все ссылки должны использовать проверяемые индексы.

## 10.5. Неизменяемость

После успешной компиляции и проверки программа должна становиться immutable.

Изменяемые данные выполнения должны находиться в отдельных рабочих областях.

Это позволяет безопасно использовать одну программу в нескольких потоках.

## 10.6. Формат сериализации

Если программы планируется сохранять на диске, необходимо отдельно определить:

- версию сериализованного формата;
- порядок байтов;
- стабильность идентификаторов;
- контрольную сумму;
- совместимость версий;
- правила миграции.

Не следует считать Java-объекты или внутренние адреса сериализуемыми идентификаторами.

Кэширование программ на диске является отдельным расширением и не должно быть обязательным для первой версии.

# 11. Байткод и виртуальная машина

## 11.1. Назначение VM

Универсальный интерпретатор должен исполнять компактную программу, не создавая Java-объект для каждой операции.

VM является общей вычислительной основой.

Листовые ядра используются для сложных операций, которые выгодно выполнять специализированным кодом.

## 11.2. Рекомендуемые группы инструкций

### Константы

```text
PUSH_CONST
PUSH_COORD_X
PUSH_COORD_Y
PUSH_COORD_Z
```

### Арифметика

```text
ADD
SUB
MUL
DIV
MIN
MAX
NEG
ABS
```

### Ограничение диапазона

```text
CLAMP
```

### Специализированные операции

```text
CALL_KERNEL
CALL_SPLINE
CALL_PERLIN
CALL_BLENDED_NOISE
```

Некоторые из этих инструкций могут быть объединены в общий `CALL_KERNEL` с индексом ядра.

### Кэширование

```text
CACHE_COLUMN_GET
CACHE_COLUMN_SET
CACHE_CELL_GET
CACHE_CELL_SET
```

Точный набор должен повторять семантику соответствующих ванильных кэш-обёрток.

### Обратные вызовы

```text
CALL_JAVA
```

### Завершение

```text
RETURN
```

Это предварительный перечень. Окончательный набор определяется после инвентаризации реальных типов узлов целевой версии Minecraft.

## 11.3. Семантика стека

Для каждой инструкции должны быть определены:

- число входных значений;
- число выходных значений;
- тип входов;
- тип выходов;
- изменение глубины стека;
- допустимые индексы;
- возможные статусы ошибки.

Пример:

| Инструкция | Вход | Выход |
|---|---:|---:|
| PUSH_CONST | 0 | 1 |
| ADD | 2 | 1 |
| MUL | 2 | 1 |
| NEG | 1 | 1 |
| ABS | 1 | 1 |
| CLAMP | 3 | 1 |
| CALL_KERNEL | По описанию | По описанию |
| RETURN | 1 | 0 |

Точное расположение операндов должно быть единообразным для всех вариантов реализации.

## 11.4. Верификация байткода

Java-верификатор должен проверить:

- допустимость opcode;
- длину инструкции;
- корректность индексов;
- доступность констант;
- доступность сэмплеров;
- допустимую глубину стека;
- отсутствие переполнения при расчёте размеров;
- корректность callback-индексов;
- допустимость диапазонов буферов;
- согласованность заголовка;
- допустимые размеры таблиц.

Если программа содержит переходы, необходимо дополнительно проверять все возможные пути исполнения.

Для первоначальной реализации предпочтительна простая линейная VM без произвольных переходов и циклов.

Это значительно упрощает проверку.

## 11.5. Ограничения

Программа не должна иметь возможности:

- обращаться к произвольным адресам;
- читать память вне таблиц;
- выполнять системные вызовы;
- создавать потоки;
- выделять память;
- исполнять произвольный машинный код.

# 12. Оптимизация программ

Оптимизации выполняются на Java-стороне до передачи программы в C.

Каждое преобразование должно сохранять семантику действующей Java-реализации.

## 12.1. Constant Folding

Предварительное вычисление выражений, содержащих только константы.

Пример:

```text
ADD(
    CONST(2.0),
    CONST(3.0)
)
```

может превратиться в:

```text
CONST(5.0)
```

Однако преобразование допустимо только при совпадении семантики арифметики.

Необходимо учитывать:

- NaN;
- Infinity;
- signed zero;
- порядок округления;
- тип промежуточных операций.

## 12.2. Common Subexpression Elimination

Общие подвыражения вычисляются один раз и используются повторно.

Условия:

- выражение действительно идентично;
- его результат не зависит от изменяемого контекста;
- оно не имеет побочных эффектов;
- повторное вычисление не имеет специальной семантики кэширования;
- порядок вычислений не меняет результат.

Нельзя автоматически объединять любые одинаковые по структуре узлы.

## 12.3. Dead Branch Removal

Удаление выражений, результат которых не используется.

Перед удалением необходимо убедиться, что выражение не влияет на поведение через контекст или специальные механизмы вычисления.

## 12.4. Column Hoisting

Перенос вычислений, зависящих только от X/Z, за пределы повторяющихся операций по Y.

Пример:

```text
Result(x, y, z) =
    ColumnValue(x, z) + VerticalValue(y)
```

Если `ColumnValue` действительно не зависит от Y и контекстных особенностей, его можно вычислить один раз на колонку.

## 12.5. Оптимизации должны быть независимыми

Каждый этап должен включаться отдельно.

Рекомендуется иметь возможность:

- отключить конкретную оптимизацию;
- сравнить результат до и после неё;
- вывести её вклад в производительность;
- локализовать несовпадение до конкретного преобразования.

## 12.6. Порядок оптимизаций

Предлагаемый порядок:

1. Построение IR.
2. Нормализация узлов.
3. Определение чистоты выражений.
4. Constant Folding.
5. Common Subexpression Elimination.
6. Dead Branch Removal.
7. Column Hoisting.
8. Слияние подходящих инструкций.
9. Построение таблиц констант.
10. Генерация байткода.
11. Верификация.
12. Расчёт подписи.

Порядок должен проверяться на реальных деревьях Minecraft.

# 13. Кэширование и интерполяция

## 13.1. Кэширование

Minecraft использует специальные обёртки, повторно использующие ранее вычисленные значения.

Нативный движок должен повторять их семантику, а не просто заменять их обычным словарём.

Необходимо изучить:

- область действия каждого кэша;
- зависимость от координат;
- зависимость от контекста ячейки;
- срок жизни значения;
- правила сброса;
- потоковую принадлежность;
- правила повторного обращения.

## 13.2. Разделение кэшей

Рекомендуемые категории:

| Категория | Предполагаемая область |
|---|---|
| Column cache | Колонка X/Z |
| Cell cache | Ячейка интерполяции |
| Point cache | Конкретная точка |
| Shared immutable data | Общие таблицы |

Это логические категории. Фактическая реализация должна соответствовать конкретным ванильным обёрткам.

## 13.3. Изоляция потоков

Если кэш изменяемый, он не должен совместно использоваться рабочими потоками без строгой синхронизации.

Предпочтительно:

- общие неизменяемые таблицы;
- локальные рабочие контексты;
- локальные буферы;
- отсутствие глобального изменяемого состояния.

## 13.4. Интерполяция ячеек

Размер стандартной ячейки:

```text
4 × 8 × 4 блока
```

Ванилла вычисляет интерполируемые значения в углах ячейки, затем получает промежуточные значения путём смешивания.

Рекомендуется переносить стандартный цикл в C.

### Требования

- идентичный порядок обхода углов;
- идентичные координаты;
- идентичный порядок вычисления;
- идентичный порядок интерполяции;
- идентичная арифметика;
- идентичное поведение при границах ячеек.

### Особое внимание

Нельзя предполагать, что математически эквивалентная перестановка операций обязательно даёт одинаковые биты.

Например, порядок смешивания значений должен воспроизводить реальную последовательность Java.

## 13.5. Нестандартные обёртки

Если обёртка не соответствует стандартному циклу интерполяции, её поддерево должно вычисляться запасным способом.

Предпочтение отдаётся корректному point-wise fallback, а не попытке принудительно включить неподдерживаемую оптимизацию.

- скрытые статические кэши без синхронизации.

# 15. Математическая точность и IEEE 754

Это один из наиболее критических разделов всего проекта.

Побитовое совпадение требует совпадения не только математических формул, но и правил вычисления.

## 15.1. Основной числовой тип

Основной тип значений плотности — IEEE 754 binary64, соответствующий Java `double`.

Необходимо сохранить:

- формат представления;
- правила округления;
- порядок операций;
- поведение специальных значений;
- правила преобразования типов.

## 15.2. Signed Zero

`+0.0` и `-0.0` математически равны, но имеют разные битовые представления.

Если проверяется побитовый паритет, их нельзя считать взаимозаменяемыми.

## 15.3. NaN

Необходимо учитывать:

- разные представления NaN;
- распространение NaN;
- канонизацию NaN;
- поведение сравнений;
- поведение MIN/MAX;
- преобразования между Java и C.

Для проверки исходных битов Java рекомендуется использовать `Double.doubleToRawLongBits`, если это соответствует выбранному определению паритета.

Использование `Double.doubleToLongBits` может скрывать различия между представлениями NaN.

Окончательная политика должна быть зафиксирована отдельным тестовым набором.

## 15.4. Infinity

Проверять:

- положительную бесконечность;
- отрицательную бесконечность;
- арифметику с бесконечностями;
- деление;
- ограничения диапазонов.

## 15.5. Subnormal Numbers

Нельзя без проверки разрешать процессору или компилятору сбрасывать субнормальные значения в ноль.

Необходимо контролировать режимы:

- FTZ;
- DAZ;
- настройки floating-point environment.

Если разные реализации работают в разных режимах, результат может отличаться.

## 15.6. FMA

Fused Multiply-Add объединяет умножение и сложение в одну операцию с единственным округлением.

Обычная последовательность:

```c
double result = a * b + c;
```

может быть преобразована компилятором в FMA.

Это может изменить последние биты результата.

Поэтому:

- режим автоматического объединения операций должен быть контролируемым;
- эталонная реализация должна воспроизводить Java-семантику;
- FMA-варианты могут существовать отдельно;
- каждый вариант должен проходить проверку.

## 15.7. Fast Math

Флаги вроде `-ffast-math` не должны использоваться для эталонных реализаций.

Они могут разрешать преобразования, несовместимые с требованием побитового совпадения.

Оптимизированные сборки также должны проходить полный тестовый корпус.

## 15.8. Системные математические функции

Особенно внимательно нужно проверять:

- sin;
- cos;
- tan;
- exp;
- log;
- pow;
- sqrt;
- floor;
- ceil;
- round;
- функции интерполяции.

Нельзя предполагать, что `libm` выдаёт те же биты, что и Java.

Для каждого такого примитива возможны три варианта:

1. Собственная эталонная реализация.
2. Вариант, прошедший эмпирическую проверку.
3. Java fallback.

## 15.9. Порядок операций

Нужно сохранять точный порядок вычисления.

Нельзя без проверки:

- менять порядок сложения;
- объединять операции;
- менять последовательность clamp;
- переставлять вычисления min/max;
- использовать алгебраические упрощения;
- менять порядок интерполяции.

## 15.10. Численная спецификация каждого ядра

Для каждого ядра рекомендуется вести документ:

```text

    Kernel ID
    Mathematical definition
    Java reference implementation
    Input types
    Output types
    Special values

    FMA policy
    NaN policy

```

## 15.11. Компиляторы

Нельзя считать, что успешная проверка одной сборки C гарантирует корректность другой.

Необходимо отдельно проверять:

- Debug;
- Release;
- LTO;
- разные версии компилятора;
- разные параметры оптимизации;
- разные системные библиотеки.

# 16. ABI и интерфейс Java/C

## 16.1. Общий контракт

Контрактом является не язык C, а ABI.

Любой язык, способный реализовать совместимый бинарный интерфейс, может использоваться для отдельных компонентов.

ABI должен определяться одним публичным C header.

## 16.2. Требования ABI

- C calling convention;
- фиксированные типы;
- явные размеры структур;
- явные версии;
- отсутствие передачи Java-объектов;
- отсутствие исключений;
- отсутствие скрытого владения памятью;
- отсутствие произвольных callback из C в Java;
- документированное владение всеми указателями.

## 16.3. Пример концептуального интерфейса

Следующий пример показывает возможное направление проектирования. Он не является окончательной спецификацией функций.

```c
#include <stdint.h>
#include <stddef.h>

#define NNA_ABI_VERSION 1

typedef struct {
    const uint8_t* code;
    uint64_t code_size;

    const double* constants;
    uint64_t constants_count;

    uint64_t instruction_count;
    uint32_t program_version;
} nna_program_view;

typedef struct {
    const double* x;
    const double* y;
    const double* z;

    uint64_t point_count;
} nna_batch_view;

typedef struct {
    double* results;
    uint64_t results_capacity;
} nna_result_view;

uint32_t nna_abi_version(void);

int32_t nna_eval_batch(
    const nna_program_view* program,
    const nna_batch_view* batch,
    nna_result_view* output
);
```

При реальной реализации необходимо дополнительно определить:

- структуру таблиц сэмплеров;
- рабочую память;
- callback-буферы;
- статусы незавершённого исполнения;
- требования к выравниванию;
- правила обработки ошибок;
- размер каждой структуры.

## 16.4. ABI Versioning

При загрузке библиотеки Java должна:

1. Получить версию ABI.
2. Проверить поддерживаемый диапазон.
3. Проверить необходимые символы.
4. Проверить размеры структур.
5. Отказаться от использования несовместимой библиотеки.

Изменение ABI должно сопровождаться увеличением версии.

## 16.5. Экспорт символов

Все публичные функции должны иметь проектный префикс.

Необходимо избегать случайного экспорта внутренних функций.

Сборка должна проверять список экспортируемых символов.

## 16.6. Статусы

Рекомендуется иметь фиксированный набор:

```text
OK
NEED_JAVA
INVALID_ARGUMENT
INVALID_PROGRAM
BUFFER_TOO_SMALL
UNSUPPORTED_OPERATION
INTERNAL_ERROR
```

Статусы должны быть документированы и иметь одинаковое значение на всех платформах.

Ошибки не должны кодироваться случайными значениями или текстовыми строками.

# 17. FFM

## 17.1. FFM

FFM является единственным механизмом взаимодействия Java и нативного кода. Проект поддерживает только версии Java, где FFM является стандартным API (Java 22 и новее), что соответствует актуальным версиям Minecraft.

Преимущества:

- современный API;
- явное управление памятью;
- работа с нативными функциями;
- удобная интеграция с C ABI.

Необходимо учитывать, что API и доступность FFM зависят от версии Java.

## 17.2. Почему JNI не используется

JNI сознательно не используется.

Проект создаётся для актуальных версий Minecraft, которые сами требуют современную Java, поэтому поддержка версий Java ниже 22 и запасной мост для них не требуются. Один механизм взаимодействия означает одну модель управления памятью и одно поведение, которое необходимо тестировать на каждой платформе, включая телефонные лаунчеры.

## 17.3. Общий Java API

Мост FFM скрыт за общей абстракцией:

```java
interface NativeBridge {

    int abiVersion();

    NativeStatus evaluateBatch(
        ProgramView program,
        BatchView batch,
        ResultView output
    );

    void close();
}
```

Реальный интерфейс должен соответствовать выбранной модели callback и управления памятью.

## 17.4. Запрет дублирования логики

Мост не должен содержать собственной вычислительной логики.

Он только передаёт данные в функции нативной библиотеки и возвращает статусы, поэтому поведение системы не зависит от деталей механизма вызова.

## 17.5. Выбор механизма

Предлагаемая последовательность:

1. Проверить доступность FFM.
2. Проверить возможность загрузки библиотеки.
3. Подключиться к библиотеке через FFM.
4. Проверить ABI.
5. Если FFM недоступен или ABI несовместим, использовать Java-only.

# 18. Память, буферы и многопоточность

## 18.1. Владение памятью

Для каждого буфера необходимо явно определить:

- кто выделяет память;
- кто изменяет содержимое;
- кто читает содержимое;
- кто освобождает память;
- сколько времени действительны указатели.

Предпочтительная модель:

Java владеет памятью и временем жизни буферов, C только использует переданные области в пределах вызова.

## 18.2. Буферы

Необходимо предусмотреть:

- входные координаты;
- результаты;
- рабочий стек;
- временные значения;
- запросы Java;
- ответы Java;
- контексты интерполяции.

## 18.3. Fixed-size workspace

Нативный движок не должен выделять память в горячем цикле.

Для этого Java заранее рассчитывает необходимую рабочую память.

Перед вызовом проверяются:

- размер пакета;
- размер программы;
- максимальная глубина стека;
- количество callback-запросов;
- размеры таблиц;
- допустимые смещения.

## 18.4. Защита от переполнения

При расчёте размеров массивов необходимо использовать проверки переполнения целых чисел.

Например, вычисление:

```text
elementCount * elementSize
```

должно проверяться до выделения или передачи буфера.

Нельзя полагаться только на то, что входные данные обычно небольшие.

## 18.5. Рабочие контексты

Рекомендуется использовать отдельный `ExecutionContext` на поток или задачу генерации.

```text
ExecutionContext
    VMStack
    Workspace
    InputBuffers
    OutputBuffers
    CallbackBuffers
    CacheState
    InterpolationState
    Statistics
```

## 18.6. Параллельная работа

Общие программы и таблицы должны быть immutable.

Рабочие данные должны принадлежать конкретному выполнению.

Необходимо проверить:

- одновременный вызов одного дерева;
- вызов разных деревьев;
- повторное использование буферов;
- завершение мира во время выполнения;
- отсутствие гонок;
- корректность публикации программ между потоками.

## 18.7. FFM Memory Safety

Нужно отдельно проверить:

- время жизни сегментов;
- доступ из разных потоков;
- выравнивание;
- границы памяти;
- закрытие ресурсов;
- отсутствие use-after-free;
- отсутствие доступа после закрытия мира.

# 19. Каталог вычислительных ядер

## 19.1. Perlin Noise

Ядро должно реализовывать:

- координатные преобразования;
- таблицу перестановок;
- вычисление градиентов;
- интерполяцию;
- октавы;
- масштабирование;
- суммирование слоёв.

Тестирование должно охватывать:

- целые координаты;
- отрицательные координаты;
- координаты около границ ячеек;
- большие координаты;
- разные сиды;
- разные таблицы перестановок;
- специальные числовые значения, если они допустимы входным контрактом.

## 19.2. BlendedNoise

Необходимо отдельно реализовать и тестировать:

- масштабирование координат;
- выбор сэмплеров;
- смешивание диапазонов;
- интерполяционные этапы;
- преобразования значений;
- граничные условия.

## 19.3. Spline

Требуется поддержать:

- контрольные точки;
- координаты;
- значения;
- производные, если они используются;
- вложенные сплайны;
- обработку границ;
- точный порядок интерполяции.

## 19.4. Арифметические ядра

Отдельно проверяются:

- сложение;
- вычитание;
- умножение;
- деление;
- отрицание;
- абсолютное значение;
- минимум;
- максимум;
- ограничение диапазона.

Для простых операций может быть выгоднее использовать инструкции VM.

## 19.5. Fused Kernels

Объединённые ядра должны сокращать dispatch overhead.

Например, последовательность из нескольких часто встречающихся операций может быть объединена в одно ядро.

Однако объединение допустимо только при сохранении:

- порядка вычисления;
- промежуточных округлений;
- поведения NaN;
- поведения signed zero.

## 19.6. Каталог вариантов

Для каждого ядра:

```text
Kernel
    ReferenceVariant
    PortableOptimizedVariant
    SIMDVariant
    SpecializedVariant
    WorkaroundVariant
```

Необязательно иметь все категории.

Эталонный вариант должен оставаться доступным всегда.

# 20. Векторизация и SIMD

## 20.1. Цель

Обрабатывать несколько независимых точек одной группой машинных инструкций.

Основные направления:

- SSE;
- AVX;
- NEON;
- другие доступные варианты.

## 20.2. Векторизация по точкам

Вместо:

```text
evaluate(point_0)
evaluate(point_1)
evaluate(point_2)
```

используется:

```text
evaluate_batch(points[])
```

Для подходящих операций координаты и промежуточные значения располагаются так, чтобы процессор мог обрабатывать несколько значений одновременно.

## 20.3. Ограничения

Табличные операции с зависимыми индексами, например обращения к таблицам перестановок, могут плохо подходить для обычной SIMD-векторизации.

Такие операции допускается оставлять скалярными.

Не следует векторизовать участок только ради формального использования SIMD.

## 20.4. Остаток пакета

Если размер пакета не кратен ширине SIMD:

- обрабатывается полная часть;
- оставшиеся элементы обрабатываются безопасным скалярным вариантом либо подходящей маской.

Нельзя допускать чтения за границами массива.

## 20.5. Тестирование

Для каждой SIMD-реализации необходимы:

- тесты всех размеров пакетов;
- тесты выравнивания;
- тесты неполных векторов;
- тесты граничных значений;
- сравнение с эталонным вариантом;
- тесты на конкретном оборудовании.

# 21. Эмпирический подбор ядер

## 21.1. Основной принцип

Машина сама проверяет доступные варианты.

Не используется жёсткая таблица вида:

```text
CPU model A -> implementation X
CPU model B -> implementation Y
```

Вместо этого:

```text
Available variants
        |
        v
Instruction-set eligibility
        |
        v
Correctness tests
        |
        v
Benchmark
        |
        v
Fastest valid variant
```

## 21.2. Этап 1. Проверка возможностей

До выполнения варианта проверяется наличие необходимых инструкций.

Также необходимо учитывать поддержку операционной системой соответствующего состояния процессора.

Одной информации о модели CPU может быть недостаточно.

## 21.3. Этап 2. Проверка корректности

Каждый вариант выполняется на верификационных векторах.

Несовпадающий вариант исключается.

## 21.4. Этап 3. Benchmark

Оставшиеся варианты тестируются на реалистичных нагрузках.

Используются:

- производственные размеры пакетов;
- прогрев;
- медианные результаты;
- несколько повторений;
- контроль выбросов;
- сравнение с эталоном.

## 21.5. Порог принятия

Новый вариант должен быть приблизительно на 5% быстрее корректного варианта по умолчанию, чтобы заменить его.

Этот порог является исходным проектным правилом.

Его необходимо дополнительно проверить на стабильность при разных размерах пакетов.

## 21.6. Кэширование результатов

Рекомендуется включать в ключ кэша:

- модель процессора;
- архитектуру;
- доступные возможности;
- сборку движка;
- ABI;
- набор вариантов;
- версию компилятора;
- существенные характеристики среды выполнения;
- версию эталонного Java Runtime, если она влияет на результаты проверки.

Это расширение исходного минимального ключа.

## 21.7. Поведение при повреждении кэша

Если таблица:

- отсутствует;
- повреждена;
- имеет неизвестную версию;
- относится к другой сборке;
- содержит неизвестный вариант;

используются консервативные настройки по умолчанию.

## 21.8. Дочерний процесс

Если платформа позволяет, профилирование подозрительных вариантов выполняется в отдельном процессе.

Это ограничивает последствия некоторых ошибок профилирования.

Но важно понимать:

**Дочерний процесс для бенчмарков не защищает игровую сессию от ошибки нативного ядра, выполняемого непосредственно внутри игры.**

Для runtime-кода необходимы отдельные меры проверки и ограничения.

## 21.9. Нагрев телефона

Android-устройства могут снижать частоты при длительной нагрузке.

Поэтому необходимо:

- избегать слишком длинных бенчмарков;
- использовать медианные измерения;
- учитывать thermal throttling;
- не повторять подбор во время игровой сессии;
- оставлять консервативный вариант при сомнительных результатах.

# 22. Система верификации

## 22.1. Общая архитектура

Верификация является обязательной частью системы, а не дополнительным диагностическим инструментом.

Её задача — не допустить включения нативного вычисления без достаточной проверки.

## 22.2. Уровень 1. Unit Vectors

Проверяются отдельные обработчики и ядра.

Категории:

1. Случайные точки.
2. Состязательные точки.
3. Граничные координаты.
4. Минимальная высота.
5. Максимальная высота.
6. Углы ячеек.
7. Точки около границ интерполяции.
8. Реальные таблицы сэмплеров.
9. Реальные сиды.
10. Специальные числовые случаи.

Для каждого входа:

```text
Java reference
      |
      v
Expected raw bits

Native implementation
      |
      v
Actual raw bits

Expected == Actual
```

## 22.3. Уровень 2. Golden Chunks

Проверяется вся скомпилированная цепочка.

Порядок:

1. Создать эталонное состояние.
2. Сгенерировать чанки Java-путём.
3. Сохранить результаты.
4. Сгенерировать те же чанки нативным путём.
5. Сравнить результаты.
6. Разрешить включение нативного пути только при успешной проверке.

## 22.4. Уровень 3. Probation

После включения нативного пути первые пакетные вычисления проверяются синхронно: результат каждого пакета сравнивается с результатом Java до того, как генератор сможет его использовать. Непроверенный результат не должен попадать в мир.

Если обнаружено несовпадение:

- генератор получает результат Java, а не нативный;
- фиксируется точка;
- сохраняются оба значения;
- определяется дерево;
- нативный путь дерева отключается.

После заданного количества успешно проверенных пакетов проверка переходит в фоновый теневой режим.

При этом shadow evaluation должна учитывать возможное состояние кэшей и контекста.

Нельзя бездумно повторно вызывать вычисления с побочными эффектами или изменять состояние генерации.

## 22.5. Уровень 4. Локализация

При несовпадении система последовательно проверяет меньшие поддеревья.

Цель:

- определить проблемный узел;
- отличить ошибку ядра от ошибки компиляции;
- определить ошибку оптимизации;
- определить ошибку интерполяции;
- определить ошибку обработки контекста.

## 22.6. Уровень 5. Иерархия отключений

```text
Primitive
    |
    v
Subtree
    |
    v
Tree
    |
    v
Dimension
    |
    v
Entire Accelerator
```

Каждое отключение должно иметь:

- причину;
- идентификатор компонента;
- подпись мира;
- временную отметку;
- уровень отключения;
- диагностические сведения.

## 22.7. Состояния проверки

Рекомендуется использовать явную машину состояний:

```text
DISCOVERED
    |
    v
COMPILED
    |
    v
STATIC_VERIFIED
    |
    v
UNIT_VERIFIED
    |
    v
GOLDEN_VERIFIED
    |
    v
PROBATION
    |
    v
ENABLED
```

Возможные дополнительные состояния:

```text
UNSUPPORTED
REJECTED
DISABLED
JAVA_ONLY
ERROR
```

Переход к `ENABLED` разрешён только после обязательных проверок.

## 22.8. Проверка должна быть воспроизводимой

Каждое несовпадение должно сопровождаться данными, позволяющими повторить проверку:

- версия Minecraft;
- версия мода;
- подпись дерева;
- подпись программы;
- версия обработчика;
- версия ядра;
- сид или его диагностический идентификатор;
- координаты;
- входные значения;
- ожидаемые биты;
- фактические биты;
- конфигурация машины.

# 23. Golden Chunks и проверка мира

## 23.1. Назначение

Golden Chunks проверяют не отдельную операцию, а результат работы всей цепочки.

Это позволяет выявить ошибки, которые не обнаруживаются модульными тестами.

Например:

- неверную компиляцию дерева;
- потерю общего подвыражения;
- ошибку порядка операций;
- неправильную работу кэша;
- ошибку интерполяции;
- ошибку передачи параметров сэмплера.

## 23.2. Требования к тестовым мирам

Тестовый корпус должен включать:

- все ванильные измерения;
- разные сиды;
- разные конфигурации датапаков;
- сложные деревья;
- деревья с кэшами;
- деревья со сплайнами;
- деревья с разными шумовыми сэмплерами;
- дополнительные пользовательские тестовые миры.

## 23.3. Сравниваемые данные

Одного хэша чанка может быть недостаточно для диагностики.

Рекомендуется сравнивать:

1. Результаты плотности, если их можно перехватить на нужном этапе.
2. Результаты шумового заполнения.
3. Содержимое блоков после соответствующей стадии.
4. Дополнительные данные, необходимые для воспроизведения.

Хэш используется как быстрый индикатор.

При несовпадении необходимо иметь возможность выполнить подробное сравнение.

Для критических тестов предпочтительно дополнительно сохранять эталонные данные или диагностические снимки.

## 23.4. Детерминизм

Перед сравнением необходимо гарантировать:

- одинаковый сид;
- одинаковую конфигурацию мира;
- одинаковые входные данные;
- одинаковую версию Minecraft;
- одинаковый набор модов;
- одинаковую стадию генерации;
- одинаковые настройки теста.

## 23.5. Локализация

Если Golden Chunk отличается, система должна постепенно уменьшать область проверки.

Однако бинарное разделение не всегда достаточно для графов с общими узлами.

Алгоритм локализации должен учитывать повторное использование поддеревьев и контекстные зависимости.

# 24. Fallback и локализация ошибок

## 24.1. Основной принцип

Неизвестный или проблемный участок не должен отключать всё дерево, если его можно безопасно вычислить на Java.

## 24.2. CALL_JAVA

`CALL_JAVA` обозначает участок программы, который вычисляется действующей Java-реализацией.

Пакетный процесс:

```text
Native VM
    |
    v
Collect callback requests
    |
    v
Return NEED_JAVA
    |
    v
Java evaluates requested nodes
    |
    v
Java writes callback results
    |
    v
Native VM resumes
    |
    v
Final results
```

## 24.3. Требования к callback

Необходимо определить:

- идентификатор callback;
- индекс точки;
- контекст узла;
- входные координаты;
- необходимые параметры;
- область памяти ответа;
- количество ответов;
- порядок соответствия запросов и результатов.

## 24.4. Отсутствие callback на каждую точку

Главное требование — не делать отдельный переход Java/C для каждой точки.

Все запросы одного этапа должны собираться в массив.

Java обрабатывает весь массив и возвращает результаты за один переход.

## 24.5. Ошибки callback

При ошибке Java-вычисления:

- выполнение нативного участка прекращается;
- текущая операция переводится в безопасный режим;
- формируется статус;
- при возможности вызывающий код использует Java-путь;
- проблема фиксируется в отчёте.

## 24.6. Ограничение callback

Количество запросов должно быть ограничено размерами переданных буферов.

Переполнение буфера не должно приводить к записи за пределами памяти.

# 25. Интеграция с Minecraft

## 25.1. Серверная сторона

Мод должен быть серверным.

На выделенном сервере устанавливается только на сервере.

В одиночной игре генерацией занимается интегрированный сервер, поэтому достаточно одной установки.

## 25.2. Основная точка подключения

Интеграция осуществляется на этапе шумового заполнения чанков.

Необходимо изучить внутренний pipeline конкретной версии Minecraft.

Точка подключения должна:

- иметь доступ к настоящему дереву;
- иметь доступ к координатам;
- сохранять порядок ванильных вычислений;
- не менять окружающий pipeline;
- корректно работать с параллельной генерацией.

## 25.3. Mixin и внутренние API

Если публичного API недостаточно, допускается использование Mixin или другого подходящего механизма загрузчика.

При этом необходимо:

- ограничить количество точек вмешательства;
- документировать каждую точку;
- проверять её на каждой версии Minecraft;
- избегать перехвата несвязанных стадий;
- предусмотреть Java-only режим при неудачном подключении.

## 25.4. Версии Minecraft

Для каждой поддерживаемой версии необходим отдельный слой адаптации.

Нельзя предполагать, что внутренние классы и типы узлов останутся неизменными.

Рекомендуемая структура:

```text
minecraft/
    common/
    v1_x/
        adapters/
        handlers/
        hooks/
```

Точная структура зависит от выбранной системы сборки и количества поддерживаемых версий.

## 25.5. Перезагрузка датапаков

При изменении конфигурации генерации необходимо определить:

- какие деревья изменились;
- какие программы можно переиспользовать;
- какие таблицы нужно пересоздать;
- какие проверки нужно повторить;
- когда старые программы можно освобождать.

Старая программа не должна использоваться после того, как изменился соответствующий источник её данных.

## 25.6. Поддержка нескольких загрузчиков

Ускоритель делится на независимое от загрузчика ядро и тонкие адаптеры под каждый загрузчик.

Ядро содержит компилятор, реестр обработчиков, верификацию, отчётность, мост FFM и работу с нативными библиотеками. Ядро зависит только от классов самой игры и стандартной библиотеки Java.

Ядро не должно импортировать API ни одного загрузчика: ни Fabric API, ни Quilt API, ни NeoForge API. Это относится и к регистрации обработчиков: она проходит через внутренний интерфейс интеграции, который реализуют адаптеры.

Внутренний интерфейс интеграции предоставляет ядру:

- событие запуска игры и завершения работы;
- подключение к стадии шумового заполнения генерации чанков;
- регистрацию обработчиков, включая обработчики внешних модов;
- доступ к конфигурации;
- сведения о платформе и версии игры.

Адаптер является единственной частью, которая знает конкретный загрузчик. Его обязанности:

- вызвать инициализацию ядра при запуске;
- зарегистрировать подключение к генерации через механизмы своего загрузчика;
- передать ядру конфигурацию и платформенные сведения.

Подключение к генерации ставится в ванильные классы игры, одинаковые под всеми загрузчиками, поэтому сам код подключения общий; различается только его регистрация.

Поддерживаемые загрузчики:

- Fabric;
- Quilt;
- NeoForge.

Forge не поддерживается. Он отличается от перечисленных загрузчиков принципиальным устройством, а не деталями API, поэтому его поддержка потребовала бы отдельной интеграции, а не ещё одного адаптера того же вида. Это зафиксированное архитектурное решение, а не отложенная задача.

Нативные библиотеки от загрузчика не зависят: одни и те же бинарники входят в сборку под каждый загрузчик. Сборка под загрузчик упаковывает ядро, нативные библиотеки и адаптер этого загрузчика.

# 26. Совместимость с другими модами

## 26.1. Полные альтернативные генераторы

Если другой мод полностью заменяет генератор мира, нативный ускоритель не должен пытаться ускорять отсутствующее ванильное дерево.

Примеры из исходной архитектуры:

- Terra;
- ReTerraForged;
- Moderner Beta.

Результат — отключение ускорителя для соответствующего мира с указанием причины.

## 26.2. Другие компиляторы

Особое внимание необходимо уделить C2ME.

Два независимых компилятора не должны одновременно управлять одним и тем же деревом.

Необходимо определить:

- механизм обнаружения;
- приоритет;
- режим совместной работы;
- поведение при неизвестной конфигурации;
- способ отключения одного из компиляторов.

Если безопасное совместное использование не подтверждено, должен применяться однозначный выбор одного владельца вычисления.

## 26.3. Неизвестные типы

Моды вроде Lithostitched и модифицированных версий Tectonic могут добавлять собственные типы узлов.

Они остаются в Java до появления соответствующих обработчиков.

## 26.4. Изменение входных данных

Biolith и TerraBlender могут изменять входные данные для размещения биомов.

Если они не изменяют математическую реализацию вычисляемых деревьев, принцип live Java oracle позволяет работать с ними без специальных математических реализаций.

Это должно подтверждаться тестированием конкретных интеграций.

## 26.5. Матрица совместимости

Рекомендуется вести отдельный документ:

| Мод | Тип взаимодействия | Статус | Требуемая проверка |
|---|---|---|---|
| C2ME | Другой компилятор | Требует согласования | Конфликт и выбор владельца |
| Tectonic | Изменение генерации | Частичная поддержка | Неизвестные узлы |
| Lithostitched | Новые типы узлов | Java fallback | Handler |
| Biolith | Изменение входов | Требует проверки | Live oracle |
| TerraBlender | Изменение входов | Требует проверки | Live oracle |
| Terra | Альтернативный генератор | Отключение | Обнаружение генератора |
| ReTerraForged | Альтернативный генератор | Отключение | Обнаружение генератора |
| Moderner Beta | Альтернативный генератор | Отключение | Обнаружение генератора |

Статус совместимости должен обновляться только после воспроизводимого тестирования.

# 30. Производительность и профилирование

## 30.1. Первоначальное профилирование

До серьёзной реализации необходимо определить, какая часть шумового этапа занимает процессорное время.

Отдельно измеряются:

- Perlin;
- BlendedNoise;
- Spline;
- арифметика;
- обход деревьев;
- кэширование;
- интерполяция;
- Java-вызовы;
- переходы между подсистемами.

## 30.2. Основная проблема

В исходной архитектуре указано, что шумовое заполнение при одном из внутренних тестов занимало приблизительно половину процессорного времени последовательной генерации новых чанков на ПК среднего класса.

Однако распределение этой доли между сэмплерами и обработкой дерева пока неизвестно.

Именно поэтому Stage 0 обязателен.

## 30.3. Benchmark Scenarios

Необходимо создать несколько сценариев.

### Сценарий A. Только листовые ядра

Измеряет стоимость отдельных вычислительных примитивов.

### Сценарий B. Полная программа

Измеряет интерпретатор, инструкции, таблицы и ядра вместе.

### Сценарий C. Программа с Java fallback

Измеряет стоимость `CALL_JAVA`.

### Сценарий D. Интерполяция

Измеряет обработку ячеек.

### Сценарий E. Полная генерация чанков

Измеряет реальное ускорение Minecraft pipeline.

### Сценарий F. Многопоточная генерация

Измеряет масштабирование и конкуренцию за ресурсы.

### Сценарий G. Android

Отдельно измеряет нагрев, стабильность частот и продолжительность нагрузки.

## 30.4. Метрики

Основные метрики:

- chunks per second;
- median chunk generation time;
- p95 chunk generation time;
- noise stage time;
- CPU time;
- native execution time;
- Java fallback time;
- callback count;
- instructions per point;
- allocations;
- memory footprint;
- throughput per worker.

## 30.5. Amdahl's Law

Даже полное ускорение шумового этапа не ускоряет остальные части генерации.

Если шум занимает долю `P` времени, а ускорение этой части равно `S`, общий коэффициент:

\[
Speedup = \frac{1}{(1-P)+\frac{P}{S}}
\]

Поэтому необходимо измерять реальный вклад оптимизируемого участка.

## 30.6. Честное сравнение

Все бенчмарки должны использовать:

- одинаковые миры;
- одинаковые сиды;
- одинаковые параметры;
- одинаковое количество потоков;
- одинаковые размеры регионов;
- прогретую JVM;
- одинаковую конфигурацию модов;
- одинаковые условия тестирования.

Необходимо отдельно публиковать:

- холодный запуск;
- прогретую генерацию;
- одиночную генерацию;
- параллельную генерацию.

## 30.7. Внешние ориентиры

В исходной архитектуре приведены заявления авторов других проектов:

- ZFastNoise — приблизительно 10–18% улучшения за счёт оптимизации хранения;
- C2ME — до 30% при определённой генерации с датапаками и до 90% с конфигурацией Tectonic.

Это заявленные авторами показатели, а не независимо подтверждённые результаты данного проекта.

Они используются только как ориентиры для будущего сравнения.

Должны запускаться на каждом существенном изменении компилятора, обработчиков и нативного движка.

## 31.10. Regression Tests

Каждое обнаруженное несовпадение превращается в постоянный регрессионный тест.

В тестовый корпус добавляется не только ошибочная координата, но и минимальный контекст, позволяющий воспроизвести проблему.

# 33. Безопасность и отказоустойчивость

## 33.1. Важное уточнение к принципу No Crashes

Отсутствие динамического выделения памяти и системного ввода-вывода уменьшает количество возможных ошибок.

Однако оно не даёт математической гарантии отсутствия падений нативного кода.

Например:

- обращение за пределы массива;
- неправильный указатель;
- use-after-free;
- ошибка выравнивания;
- ошибка в SIMD-коде;
- несовместимая инструкция;
- повреждение стека.

Поэтому принцип следует формулировать точнее:

**Архитектура должна минимизировать последствия ошибок и предотвращать выполнение некорректных программ настолько, насколько это возможно средствами статической проверки, ограниченных буферов, тестирования и безопасного fallback.**

Ошибки уровня сегментации в процессе игры могут завершить процесс независимо от Java fallback.

## 33.2. Границы доверия

Нужно считать потенциально недоверенными:

- данные датапаков;
- сложность пользовательских деревьев;
- сторонние обработчики;
- скомпилированные программы;
- данные, поступающие через ABI;
- сторонние библиотеки.

## 33.3. Защита от чрезмерно сложных деревьев

Рекомендуемые ограничения:

- максимальная глубина дерева;
- максимальное число узлов;
- максимальное число инструкций;
- максимальный размер таблиц;
- максимальный размер пакета;
- максимальная глубина стека;
- максимальное количество callback.

При превышении лимита соответствующее дерево должно перейти на Java.

## 33.4. Защита ABI

Java должна проверять все входные размеры до передачи данных.

C должен выполнять минимальные защитные проверки:

- null;
- размеры;
- индексы;
- допустимые диапазоны;
- согласованность структур.

Защита должна присутствовать с обеих сторон.

## 33.5. Fault Isolation

Ошибка отдельного обработчика не должна повреждать всю систему.

Ошибка одного дерева не должна отключать остальные деревья.

Ошибка ядра должна приводить к его отключению.

Ошибка ABI или нативной библиотеки может потребовать отключения всего ускорителя.

## 33.6. Сохранение состояния

Результаты успешного подбора можно сохранять на диске.

Результаты временных отказов конкретного мира не должны безусловно переноситься на другой мир.

Каждое отключение должно быть связано с соответствующей подписью мира и контекстом проверки.

# 34. Поддержка дополнительных языков

## 34.1. ABI как основа

Статус направления: отложено на длительный срок. Раздел фиксирует только принципы на будущее; до стабилизации ядра и ABI работа по дополнительным языкам не ведётся.

Движок определяется бинарным интерфейсом, а не языком реализации.

Допускаются:

- C;
- C++;
- Rust;
- Zig;
- ассемблер.

## 34.2. Общая библиотека

Пример:

```text
C Core
  |
  +-- Rust Kernel
  |
  +-- Assembly Kernel
  |
  +-- C SIMD Kernel
  |
  v
Shared Linker
  |
  v
Single Native Library
```

Java видит одну библиотеку и один ABI.

## 34.3. Требования

Через ABI не должны проходить:

- исключения;
- Rust panic;
- объекты с неясным временем жизни;
- скрытое выделение памяти;
- внутренние планировщики потоков;
- зависимости от собственной сборки мусора.

## 34.4. Rust

Для Rust необходимо:

- использовать `extern "C"`;
- ограничить панику внутри FFI;
- не допускать unwinding через ABI;
- использовать совместимые типы;
- не передавать владение памятью без явного контракта.

## 34.5. C++

Для C++ необходимо:

- использовать C ABI-обёртки;
- не экспортировать C++-классы;
- не передавать исключения;
- контролировать стандартную библиотеку;
- избегать скрытых runtime-зависимостей.

## 34.6. Ассемблер

Ассемблер может использоваться для отдельных ядер, если:

- есть переносимый эталон;
- есть тестовые векторы;
- проверены границы памяти;
- проверены требования к инструкциям;
- есть безопасный fallback.

|---|---|---|
| Различия floating-point | Изменение плотности | Raw-bit differential tests |

# 40. Рекомендуемые архитектурные решения (ADR)

Для предотвращения незаметного изменения архитектуры рекомендуется вести отдельные Architecture Decision Records.

Каждое решение должно содержать:

- номер ADR;
- дату;
- проблему;
- рассмотренные варианты;
- принятое решение;
- причины;
- последствия;
- связанные тесты.

## ADR-001. Побитовый паритет

**Решение:** Java является эталоном. Допуск нативного кода возможен только после проверки.

## ADR-002. Частичная компиляция

**Решение:** неподдерживаемые поддеревья передаются Java через `CALL_JAVA`.

## ADR-003. Batch Execution

**Решение:** каждый нативный вызов обрабатывает массивы точек.

## ADR-004. Отсутствие runtime code generation

**Решение:** используется фиксированный движок и подготовленные программы.

## ADR-005. ABI Independence

**Решение:** публичный контракт определяется ABI, а не языком реализации.

## ADR-006. FFM

**Решение:** FFM является единственным механизмом взаимодействия. JNI не используется: поддерживаются только версии Java 22 и новее, соответствующие актуальным версиям Minecraft.

## ADR-007. Reference Kernels

**Решение:** у каждого критического ядра есть переносимый эталонный вариант.

## ADR-008. Empirical Selection

**Решение:** оптимизированные варианты тестируются на конкретной машине.

## ADR-009. Immutable Programs

**Решение:** программы и общие таблицы после публикации неизменяемы.

## ADR-010. Per-world Verification

**Решение:** корректность выбранной конфигурации проверяется отдельно для каждого мира.

## ADR-011. Java Fallback

**Решение:** неподдерживаемая функциональность не блокирует остальную компиляцию.

## ADR-012. Server-side Only

**Решение:** клиентская установка не требуется.

Новые решения должны оформляться отдельными ADR, а не незаметно изменять существующие договорённости.

## 43.1. Происхождение проекта

Идея Native Noise Accelerator появилась во время разработки Far Plane Two Continuation.

Логи производительности показали значительную стоимость ванильной генерации шума.

Новый проект развивает эту идею в самостоятельный серверный ускоритель с нативным движком, компилятором деревьев функций плотности и системой автоматической проверки корректности.

## 43.2. Заключительное архитектурное правило

Вся система должна подчиняться следующему порядку приоритетов:

1. Корректность генерации.
2. Безопасность выполнения.
3. Воспроизводимость результатов.
4. Совместимость.
5. Диагностируемость.
6. Производительность.
7. Расширяемость.

Эти приоритеты нельзя менять местами ради получения более высоких показателей в бенчмарках.

**Главная задача Native Noise Accelerator — не просто выполнить генерацию мира быстрее, а сделать это без изменения результата, который получила бы настоящая Java-реализация установленной сборки Minecraft.**

Если конкретная операция не проходит проверку, она остаётся в Java.

Если отдельное ядро не подходит процессору, выбирается другой вариант.

Если целое дерево не проходит проверку, оно отключается.

Если нативная библиотека недоступна, мод продолжает работать без ускорения.

Таким образом, нативное ускорение является контролируемой оптимизацией существующего генератора, а не заменой его поведения.
