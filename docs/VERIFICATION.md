# Verification Specification

**Статус:** техническая спецификация системы проверки корректности Native Noise Accelerator.  
**Основа:** `PROJECT_ARCHITECTURE.md`, `DETAILED_ARCHITECTURE_PLAN.md`, разделы 15, 22, 23, 24, 31 и 33, `NUMERICAL_SEMANTICS.md`.  
**Назначение:** определить обязательные процедуры проверки Java-компилятора, байткода, нативных ядер, взаимодействия Java/C, генерации чанков и автоматического отключения некорректных компонентов.

Документ описывает требуемую архитектуру и критерии готовности. Наличие описанной процедуры не означает, что она уже реализована или пройдена.

---

# 1. Основной принцип

Верификация является обязательной частью Native Noise Accelerator.

Ни один нативный результат не должен использоваться генератором Minecraft без предусмотренной для соответствующего уровня проверки.

Java-реализация действующей версии Minecraft является источником истины.

Основное требование:

**Для одинаковых входных данных нативная реализация должна возвращать тот же результат, что и действующая Java-реализация.**

Для значений `double` сравниваются битовые представления, а не только числовое равенство.

Допуск относительной или абсолютной погрешности не заменяет побитовую проверку.

Если корректность конкретной операции не подтверждена, вычисление должно оставаться на Java.

## 1.1. Приоритеты

Порядок приоритетов:

1. Корректность генерации.
2. Безопасность выполнения.
3. Воспроизводимость.
4. Изоляция ошибок.
5. Совместимость.
6. Диагностируемость.
7. Производительность.

Ни один показатель производительности не может оправдывать использование некорректного вычислительного пути.

## 1.2. Область проверки

Система должна проверять:

- Java-компилятор;
- обработчики узлов;
- промежуточное представление;
- оптимизатор;
- байткод;
- статический верификатор;
- виртуальную машину;
- вычислительные ядра;
- Java/C ABI;
- FFM bridge;
- Java fallback;
- кэширование;
- интерполяцию;
- многопоточность;
- интеграцию с Minecraft;
- результаты генерации чанков.

# 2. Архитектура верификации

Система состоит из нескольких независимых уровней.

```text
                 Java Reference
                       |
                       v
              Verification Inputs
                       |
          +------------+------------+
          |                         |
          v                         v
    Java Execution           Native Execution
          |                         |
          v                         v
     Expected Bits             Actual Bits
          |                         |
          +------------+------------+
                       |
                       v
                Bit Comparison
                       |
             +---------+---------+
             |                   |
             v                   v
          MATCH               MISMATCH
             |                   |
             v                   v
      Continue Checks       Diagnostics
                                 |
                                 v
                         Failure Localization
                                 |
                                 v
                         Disable / Fallback
```

## 2.1. Уровни проверки

| Уровень | Назначение | Обязательность |
|---|---|---|
| Static Verification | Проверка структуры программы | Всегда |
| Unit Vectors | Проверка отдельных операций | Всегда |
| Differential Testing | Сравнение Java и C | Всегда |
| Golden Chunks | Проверка полной цепочки | Для допуска дерева |
| Probation | Проверка рабочих пакетов | При включении |
| Runtime Monitoring | Контроль дальнейшего выполнения | По конфигурации |
| Failure Localization | Поиск проблемного компонента | При несовпадении |
| Regression Testing | Предотвращение повторных ошибок | Постоянно |

Проверки должны выполняться в установленной последовательности.

Невыполнение обязательного этапа запрещает переход к следующему состоянию допуска.

## 2.2. Разделение ответственности

**Compiler Verification**

Проверяет корректность преобразования дерева функций плотности в программу.

**Program Verification**

Проверяет безопасность и структурную корректность байткода.

**Kernel Verification**

Проверяет математическое поведение отдельных ядер.

**Runtime Verification**

Проверяет реальные вычисления и состояние исполнения.

**World Verification**

Проверяет соответствие результатов генерации мира.

**Failure Management**

Управляет отключением компонентов и переходом на Java.

Эти подсистемы не должны объединяться в один механизм, который невозможно диагностировать независимо.

# 3. Java Reference

## 3.1. Источник эталонных результатов

Эталонные значения должны вычисляться действующей Java-реализацией Minecraft.

Нельзя использовать в качестве единственного эталона вторую реализацию того же алгоритма, написанную специально для тестирования.

Java reference должен соответствовать:

- точной версии Minecraft;
- соответствующей реализации функций плотности;
- используемым параметрам сэмплеров;
- контексту вычисления;
- правилам кэширования;
- правилам интерполяции;
- порядку операций;
- конфигурации генерации.

## 3.2. Одинаковые входные данные

При сравнении Java и C необходимо обеспечить идентичность входов.

Проверяются:

- координаты;
- сид;
- параметры сэмплера;
- таблицы констант;
- контекст вычисления;
- состояние соответствующих кэшей;
- параметры интерполяции;
- версия программы.

Если вычисление зависит от состояния, одного совпадения координат недостаточно.

## 3.3. Независимость эталона

Java reference должен исполнять исходную логику, а не повторно использовать результат нативного вычисления.

Запрещено:

- подменять Java-результат нативным;
- получать ожидаемые значения из проверяемого ядра;
- использовать ранее сохранённый результат без проверки соответствия контекста;
- скрывать несовпадение предварительной нормализацией.

Для регрессионных тестов допускается использовать заранее сохранённые эталонные результаты при наличии полного описания условий их получения.

# 4. Сравнение численных результатов

## 4.1. Побитовое сравнение

Для `double` основной способ получения битового представления в Java:

```java
long bits = Double.doubleToRawLongBits(value);
```

Сравнение:

```java
long expectedBits = Double.doubleToRawLongBits(expected);
long actualBits = Double.doubleToRawLongBits(actual);

boolean matches = expectedBits == actualBits;
```

Числовое сравнение `expected == actual` недостаточно.

## 4.2. NaN

Политика NaN определяется `NUMERICAL_SEMANTICS.md` и спецификацией конкретного ядра.

Необходимо учитывать:

- возможную канонизацию;
- сохранение payload;
- поведение Java-операции;
- преобразования через ABI;
- различия между quiet и signaling NaN, если они применимы.

Нельзя автоматически считать все представления NaN эквивалентными.

## 4.3. Массивы результатов

Для пакетных вычислений сравнение должно проверять каждый элемент.

Недостаточно сравнить:

- среднее значение;
- сумму;
- максимальную погрешность;
- общий хэш;
- количество совпавших элементов.

Результат считается прошедшим проверку только при выполнении контракта для каждого элемента.

## 4.4. Диагностика

При несовпадении записываются:

- ожидаемое значение;
- фактическое значение;
- ожидаемые raw bits;
- фактические raw bits;
- индекс элемента;
- входные координаты;
- идентификатор программы;
- идентификатор ядра;
- версия обработчика;
- контекст вычисления.

Десятичное форматирование не заменяет сохранение исходных битов.

# 5. Уровень 1: Static Verification

## 5.1. Назначение

Статическая проверка выполняется до передачи программы нативному движку.

Её задача — исключить структурно некорректные программы и опасные ссылки на данные.

Статическая проверка не доказывает математическую корректность программы. Она подтверждает, что программа соответствует формату и может безопасно передаваться следующему этапу.

## 5.2. Проверка заголовка

Необходимо проверить:

- версию формата;
- версию набора инструкций;
- количество инструкций;
- количество констант;
- количество сэмплеров;
- количество callback-описаний;
- максимальную глубину стека;
- ожидаемое количество результатов;
- контрольную сумму.

Все размеры должны проверяться до выделения или обращения к соответствующим буферам.

## 5.3. Проверка инструкций

Для каждой инструкции проверяются:

- допустимость opcode;
- количество операндов;
- типы операндов;
- допустимость индексов;
- корректность ссылок на таблицы;
- соответствие семантике инструкции;
- отсутствие некорректных переходов;
- соблюдение ограничений программы.

Неизвестный opcode должен приводить к отклонению программы.

Нельзя интерпретировать неизвестную инструкцию как NOP.

## 5.4. Проверка стека

Для каждой инструкции необходимо знать:

- количество входных значений;
- количество выходных значений;
- изменение глубины стека;
- допустимые типы значений;
- максимальную глубину;
- возможность underflow;
- возможность overflow.

Проверяются все достижимые пути исполнения.

Если формат программы предусматривает переходы, необходимо проверить согласованность глубины стека на точках объединения потоков управления.

Для линейной программы должна быть подтверждена корректность последовательности операций от начала до `RETURN`.

## 5.5. Проверка таблиц

Проверяются:

- границы таблицы констант;
- границы таблицы сэмплеров;
- размеры spline-структур;
- ссылки на callback;
- корректность вложенных индексов;
- отсутствие арифметического переполнения при расчёте смещений.

Нельзя полагаться на то, что программа была создана внутренним Java-компилятором и поэтому автоматически безопасна.

## 5.6. Проверка CALL_JAVA

Для каждого callback проверяются:

- существование идентификатора;
- соответствие описания операции;
- допустимый контекст;
- размер буфера;
- количество запросов;
- допустимые индексы;
- соответствие ожидаемого количества результатов;
- возможность безопасного завершения при ошибке.

## 5.7. Ограничения сложности

Должны существовать ограничения на:

- количество инструкций;
- размер таблиц;
- максимальную глубину стека;
- число callback;
- размер вложенных структур;
- общую сложность программы.

Лимиты должны быть централизованными и проверяемыми.

Превышение лимита должно приводить к структурированной ошибке, а не к повреждению памяти.

## 5.8. Результат

Статический верификатор возвращает структурированный результат:

```text
ProgramVerificationResult
    accepted
    programSignature
    instructionCount
    constantCount
    maximumStackDepth
    callbackCount
    errors[]
    warnings[]
```

Это логическая схема, а не обязательное имя Java-класса.

Программа с ошибками не передаётся в нативное исполнение.

# 6. Уровень 2: Unit Vectors

## 6.1. Назначение

Проверяются отдельные обработчики, операции VM и вычислительные ядра.

Для каждого входного вектора выполняются:

1. Подготовка входных данных.
2. Вычисление Java reference.
3. Получение ожидаемых битов.
4. Вычисление нативным вариантом.
5. Получение фактических битов.
6. Сравнение.
7. Сохранение диагностики при несовпадении.

## 6.2. Категории входных данных

Обязательные категории:

| Категория | Содержание |
|---|---|
| Random | Случайные входы |
| Adversarial | Специально подобранные входы |
| Boundary | Границы допустимых диапазонов |
| Coordinates | Координаты мира |
| Cell Corners | Углы интерполяционных ячеек |
| Interpolation | Точки около границ интерполяции |
| Samplers | Реальные таблицы сэмплеров |
| World Seeds | Реальные сиды |
| Special Values | NaN, Infinity, signed zero |
| Subnormal | Субнормальные значения |
| Rounding | Граничные случаи округления |

## 6.3. Тесты отдельных ядер

Для Perlin, BlendedNoise и других сложных ядер необходимо проверять:

- обычные входные значения;
- минимальные и максимальные координаты;
- отрицательные координаты;
- переходы между ячейками;
- граничные значения параметров;
- реальные таблицы перестановок;
- реальные параметры октав;
- специальные численные случаи;
- различные сиды.

Тестовые данные должны соответствовать реальным параметрам Minecraft.

## 6.4. Тесты арифметики VM

Для каждой инструкции проверяются:

- обычные конечные значения;
- положительные и отрицательные операнды;
- нули;
- отрицательные нули;
- Infinity;
- NaN;
- субнормальные числа;
- переполнение;
- округление;
- граничные случаи.

Для `MIN`, `MAX`, `DIV`, `CLAMP` и других операций со специальными правилами необходимо использовать именно соответствующий Java reference.

## 6.5. Воспроизводимость случайных тестов

Случайные тесты должны использовать фиксируемый seed генератора тестовых данных.

При обнаружении ошибки необходимо сохранять:

- seed генератора;
- номер теста;
- входные значения;
- параметры окружения.

Это позволяет повторить случайный тест без необходимости повторно искать тот же вход.

# 7. Уровень 3: Differential Testing

## 7.1. Основной механизм

Differential Testing — основной метод проверки численной корректности.

Java и нативная реализация вычисляют один и тот же набор входных данных.

Сравниваются результаты каждой точки.

```text
                  Input Batch
                       |
              +--------+--------+
              |                 |
              v                 v
         Java Reference     Native Engine
              |                 |
              v                 v
          Expected[]         Actual[]
              |                 |
              +--------+--------+
                       |
                       v
                 Raw Bit Compare
                       |
              +--------+--------+
              |                 |
              v                 v
           All Match         Mismatch
              |                 |
              v                 v
          Pass Test          Record Failure
```

## 7.2. Требования

Java и C должны получать:

- одинаковые координаты;
- одинаковые константы;
- одинаковые параметры сэмплеров;
- одинаковую конфигурацию;
- одинаковые входные массивы;
- согласованный контекст вычисления.

Для операций с кэшированием необходимо учитывать состояние кэша и порядок вызовов.

## 7.3. Дифференциальная проверка оптимизаций

Каждое оптимизированное преобразование проверяется независимо.

Это относится к:

- Constant Folding;
- Common Subexpression Elimination;
- Dead Branch Removal;
- Column Hoisting;
- объединению операций;
- специализированным ядрам;
- SIMD;
- FMA.

Рекомендуется сравнивать три результата:

1. Оригинальный Java-граф.
2. Неоптимизированная скомпилированная программа.
3. Оптимизированная программа.

Это помогает отличить ошибку компилятора от ошибки оптимизатора и нативного ядра.

## 7.4. Дифференциальная проверка ABI

Отдельно проверяется передача значений через Java/C ABI:

- обычные `double`;
- отрицательный ноль;
- Infinity;
- NaN;
- субнормальные значения;
- большие и малые конечные значения.

Проверяются как входные, так и выходные буферы.

## 7.5. Критерий прохождения

Тест проходит, если все обязательные результаты соответствуют численному контракту.

Одна несовпадающая точка означает провал соответствующего теста.

Для операций, контракт которых требует побитовой воспроизводимости, обязательное сравнение выполняется по raw bits. Численные допуски, если они предусмотрены отдельным контрактом API с обоснованной вариативностью, могут использоваться для диагностики и оценки именно этой операции, но не могут переопределить провал обязательного критерия, перевести `FAIL` в `PASS` или разрешить нативный путь при несовпадении.

Нельзя скрывать отдельные ошибки усреднением результатов.

# 8. Уровень 4: Golden Chunks

## 8.1. Назначение

Golden Chunks проверяют всю цепочку исполнения, а не только отдельные математические функции.

Они позволяют обнаруживать проблемы:

- компиляции дерева;
- потери общих подвыражений;
- изменения порядка операций;
- кэширования;
- интерполяции;
- передачи параметров сэмплеров;
- интеграции с Minecraft;
- обработки контекста.

## 8.2. Тестовый корпус

Корпус должен включать:

- все ванильные измерения;
- несколько разных сидов;
- разные конфигурации датапаков;
- сложные деревья функций плотности;
- деревья с кэшированием;
- деревья со сплайнами;
- разные шумовые сэмплеры;
- пользовательские тестовые миры.

Покрытие должно расширяться по мере обнаружения новых проблем и появления новых поддерживаемых конфигураций.

## 8.3. Порядок проверки

1. Создать эталонное состояние мира.
2. Зафиксировать версию Minecraft.
3. Зафиксировать набор модов.
4. Зафиксировать сид.
5. Зафиксировать конфигурацию генерации.
6. Сгенерировать тестовые чанки Java-путём.
7. Сохранить эталонные результаты.
8. Воспроизвести те же условия нативным путём.
9. Сравнить результаты.
10. Сохранить диагностику.
11. Разрешить допуск только при успешном прохождении.

Java и нативный тест не должны менять общие исходные данные между прогонами.

## 8.4. Сравниваемые данные

Предпочтительно сравнивать:

1. Значения плотности на доступной стадии.
2. Результаты шумового заполнения.
3. Содержимое блоков после соответствующей стадии.
4. Дополнительные данные, необходимые для воспроизведения.

Хэш чанка используется как быстрый индикатор несовпадения.

Хэш не заменяет подробное сравнение.

При несовпадении необходимо иметь возможность определить конкретные различающиеся значения.

## 8.5. Детерминизм

Обязательные условия:

- одинаковый сид;
- одинаковая версия Minecraft;
- одинаковые моды;
- одинаковые датапаки;
- одинаковые настройки мира;
- одинаковые входные координаты;
- одинаковая стадия генерации;
- одинаковая конфигурация теста.

Нельзя сравнивать результаты разных конфигураций и интерпретировать различия как ошибку нативного движка.

## 8.6. Golden Data

Для каждого эталонного набора рекомендуется сохранять:

```text
Golden Test
    Test ID
    Minecraft Version
    Mod Version
    Dimension
    World Seed
    World Configuration
    Datapack Fingerprint
    Mod Set Fingerprint
    Chunk Coordinates
    Generation Stage
    Expected Data
    Expected Hash
    Creation Metadata
```

Эталонные данные должны быть связаны с точной конфигурацией, при которой они были созданы.

При изменении версии Minecraft или семантики генерации старые результаты нельзя автоматически считать действительными.

## 8.7. Локализация Golden Chunk

Если чанки различаются:

1. Сравнить результаты отдельных стадий.
2. Определить первую стадию с несовпадением.
3. Проверить соответствующие значения плотности.
4. Сузить область до проблемного дерева.
5. Проверить поддеревья.
6. Проверить кэширование и интерполяцию.
7. Проверить отдельные ядра.

При разделении графа необходимо учитывать общие узлы и контекстные зависимости.

Обычное бинарное деление не всегда корректно для графов с повторным использованием поддеревьев.

# 9. Уровень 5: Probation

## 9.1. Назначение

Probation — обязательный этап после предварительного допуска нативной программы.

Даже успешные предварительные тесты не гарантируют корректность всех рабочих входов.

Поэтому первые реальные пакетные вычисления должны проверяться синхронно.

## 9.2. Синхронная проверка

Порядок:

1. Получить пакет координат.
2. Выполнить нативное вычисление.
3. Выполнить соответствующее Java-вычисление.
4. Сравнить каждый результат.
5. При совпадении передать результат генератору.
6. При несовпадении передать Java-результат.
7. Записать диагностические сведения.

**Непроверенный нативный результат не должен попадать в мир.**

## 9.3. Несовпадение во время Probation

При обнаружении ошибки:

- Java-результат используется вместо нативного;
- фиксируется координата;
- сохраняются ожидаемые и фактические значения;
- определяется программа;
- определяется затронутое дерево;
- нативный путь дерева отключается;
- событие записывается в диагностический отчёт.

Ошибка не должна приводить к использованию частично проверенного пакета.

## 9.4. Переход в рабочий режим

После установленного количества успешно проверенных пакетов система может перейти в состояние `ENABLED`.

Количество пакетов должно определяться конфигурацией или централизованной политикой проверки.

Нельзя переходить к `ENABLED`, если обязательные проверки не завершены.

## 9.5. Shadow Evaluation

После Probation фоновая проверка в теневом режиме не является общим режимом для всех узлов. Она допускается только для узлов и поддеревьев, существующие характеристики IR или дескриптора которых явно подтверждают возможность безопасного независимого повторного вычисления. При принятии решения используются имеющиеся семантические характеристики (`purity`, `stateBehavior`, `sideEffectBehavior`, `cacheSemantics`, `contextRequirements`, `evaluationConstraints`); неизвестные или отсутствующие сведения трактуются как запрет, а не как признак чистоты.

Фоновая Shadow Evaluation безусловно запрещена для узлов и поддеревьев, которые:

- имеют изменяемое состояние;
- выполняют наблюдаемые побочные эффекты;
- зависят от порядка вызовов;
- привязаны к живому изменяемому контексту выполнения, включая `NoiseChunk`, его кэши и связанные объекты.

Такие узлы могут проверяться синхронно в исходном контексте либо в специально подготовленном независимом контексте, если эквивалентность и изоляция такого контекста доказаны. Если безопасная проверка невозможна, узел остаётся на Java-пути; повторно вычислять его в фоне запрещено.

Для допущенных чистых узлов необходимо учитывать семантику кэшей и все необходимые данные контекста. Теневое вычисление не должно изменять состояние генерации, кэши или уже переданные генератору данные.

# 10. Java Fallback и CALL_JAVA

## 10.1. Основной принцип

Неизвестный или неподдерживаемый узел не должен автоматически отключать всё дерево.

Если его можно безопасно вычислить действующей Java-реализацией, компилятор должен использовать `CALL_JAVA`.

## 10.2. Пакетный процесс

```text
Native VM
    |
    v
Collect callback requests
    |
    v
Return NEED_JAVA
    |
    v
Java evaluates requested nodes
    |
    v
Java writes callback results
    |
    v
Native VM resumes
    |
    v
Final results
```

## 10.3. Контракт callback

Каждый запрос должен иметь однозначную связь с:

- идентификатором callback;
- идентификатором программы;
- индексом точки;
- контекстом вычисления;
- входными координатами;
- необходимыми параметрами;
- областью выходного буфера;
- ожидаемым количеством ответов.

Результаты должны возвращаться в правильном порядке.

## 10.4. Пакетирование

Отдельный переход Java/C для каждой точки запрещён архитектурным контрактом.

Запросы одного этапа должны собираться в массив.

Java обрабатывает массив и возвращает результаты пакетно.

Размеры массива и количество ответов должны проверяться до чтения и записи.

## 10.5. Ошибки callback

При ошибке:

1. Прекратить текущее нативное выполнение.
2. Не использовать неполный результат.
3. Сформировать структурированный статус.
4. Передать вычисление безопасному Java-пути, если это возможно.
5. Зафиксировать ошибку.
6. Отключить затронутую программу при необходимости.

Нельзя возвращать фиктивное успешное значение вместо результата.

## 10.6. Ограничения памяти

Необходимо проверять:

- размер входного буфера;
- размер выходного буфера;
- количество callback;
- индекс каждого элемента;
- допустимые смещения;
- переполнение при расчёте размеров;
- соответствие количества запросов количеству ответов.

Переполнение буфера не должно приводить к выходу за границы памяти.

# 11. Локализация ошибок

## 11.1. Назначение

При несовпадении необходимо определить минимальный компонент, ответственный за проблему.

Недостаточно просто отключить ускоритель без диагностической информации.

## 11.2. Последовательность локализации

Рекомендуемая последовательность:

1. Проверить передачу входных данных.
2. Проверить Java/C ABI.
3. Проверить отдельное ядро.
4. Проверить соответствующий обработчик.
5. Проверить сгенерированные инструкции.
6. Проверить оптимизации.
7. Проверить кэширование.
8. Проверить интерполяцию.
9. Проверить контекст.
10. Проверить полное дерево.

## 11.3. Проверка поддеревьев

Если корневое вычисление отличается:

- определить участвующие узлы;
- сравнить результаты поддеревьев;
- постепенно уменьшать область;
- учитывать повторное использование общих узлов;
- проверять контекстные зависимости.

Нельзя предполагать, что каждое дерево является независимым набором узлов.

## 11.4. Категории ошибок

Рекомендуется классифицировать ошибки:

| Категория | Пример |
|---|---|
| INPUT_MISMATCH | Различаются входные данные |
| ABI_MISMATCH | Ошибка передачи значений |
| KERNEL_MISMATCH | Ошибка вычислительного ядра |
| COMPILER_MISMATCH | Неверная компиляция узла |
| OPTIMIZER_MISMATCH | Ошибка преобразования программы |
| CACHE_MISMATCH | Несоответствие кэширования |
| INTERPOLATION_MISMATCH | Ошибка интерполяции |
| CALLBACK_ERROR | Ошибка Java callback |
| CONTEXT_MISMATCH | Неверный контекст |
| MEMORY_ERROR | Ошибка работы с буферами |
| UNKNOWN_ERROR | Причина пока не установлена |

Неизвестная причина не должна заменяться предположением.

# 12. Иерархия отключений

## 12.1. Уровни

```text
Primitive
    |
    v
Subtree
    |
    v
Tree
    |
    v
Dimension
    |
    v
Entire Accelerator
```

## 12.2. Primitive

Используется, если ошибка достоверно локализована в конкретной операции или ядре.

Другие независимые и проверенные реализации могут продолжать работу.

## 12.3. Subtree

Используется, если проблема ограничена конкретным поддеревом.

При наличии безопасного Java fallback соответствующий участок вычисляется на Java.

## 12.4. Tree

Используется, если невозможно гарантировать корректность всего дерева.

Другие деревья могут продолжать работу, если они независимы и прошли необходимые проверки.

## 12.5. Dimension

Используется, если проблема затрагивает конфигурацию или общий контекст измерения.

## 12.6. Entire Accelerator

Полное отключение применяется, если ошибка затрагивает общую инфраструктуру, безопасность исполнения или несколько независимых компонентов и её нельзя безопасно локализовать.

## 12.7. Запись отключений

Каждое отключение должно содержать:

- причину;
- идентификатор компонента;
- уровень отключения;
- подпись мира;
- подпись программы;
- временную отметку;
- версию Minecraft;
- версию мода;
- сведения об ошибке;
- информацию о выбранном fallback.

Отключение должно быть детерминированным и не зависеть от случайного порядка потоков.

# 13. Машина состояний верификации

## 13.1. Основные состояния

```text
DISCOVERED
    |
    v
COMPILED
    |
    v
STATIC_VERIFIED
    |
    v
UNIT_VERIFIED
    |
    v
GOLDEN_VERIFIED
    |
    v
PROBATION
    |
    v
ENABLED
```

## 13.2. Дополнительные состояния

```text
UNSUPPORTED
REJECTED
DISABLED
JAVA_ONLY
ERROR
```

## 13.3. Значение состояний

| Состояние | Значение |
|---|---|
| DISCOVERED | Дерево обнаружено |
| COMPILED | Программа создана |
| STATIC_VERIFIED | Структура проверена |
| UNIT_VERIFIED | Модульные тесты пройдены |
| GOLDEN_VERIFIED | Проверка Golden Chunks пройдена |
| PROBATION | Выполняется синхронная рабочая проверка |
| ENABLED | Нативный путь допущен |
| UNSUPPORTED | Нет поддерживаемой реализации |
| REJECTED | Программа отклонена проверкой |
| DISABLED | Компонент отключён |
| JAVA_ONLY | Используется только Java |
| ERROR | Произошла ошибка инфраструктуры |

## 13.4. Правила переходов

- Нельзя перейти в `STATIC_VERIFIED` без успешной статической проверки.
- Нельзя перейти в `UNIT_VERIFIED` без прохождения обязательных тестов.
- Нельзя перейти в `GOLDEN_VERIFIED` без проверки соответствующего контекста.
- Нельзя перейти в `PROBATION` при наличии неразрешённых обязательных ошибок.
- Нельзя перейти в `ENABLED` до завершения Probation.
- Из `ENABLED` допускается переход в `DISABLED` при обнаружении ошибки.
- При невозможности безопасного исполнения используется `JAVA_ONLY`.

Переходы должны быть централизованы, а не выполняться произвольными компонентами.

## 13.5. Повторный допуск

Отключённый компонент не должен автоматически включаться после произвольного таймера.

Повторный допуск возможен после:

1. Исправления причины.
2. Изменения версии компонента или ядра.
3. Повторного прохождения обязательных тестов.
4. Успешной повторной проверки соответствующего контекста.

Старый отрицательный результат нельзя игнорировать без объяснимой причины его недействительности.

Диагностические отчёты не должны автоматически содержать секреты окружения, пароли или произвольное содержимое пользовательских файлов.

Сид мира и другие потенциально чувствительные сведения должны обрабатываться в соответствии с настройками диагностики.

## 14.3. Формат отчёта

Рекомендуется формировать машинно-читаемый отчёт и краткое текстовое представление.

Текстовый отчёт должен показывать:

- общий статус;
- число проверенных программ;
- число допущенных программ;
- число отключённых программ;
- причины отключений;
- долю нативного покрытия;
- количество ошибок;
- выбранные ядра;
- сведения о производительности.

Процент покрытия не должен интерпретироваться как показатель корректности.

## 14.4. Сохранение воспроизводимого случая

Для каждой найденной ошибки необходимо сохранять минимальный набор данных, позволяющий воспроизвести её.

По возможности следует сохранять:

- минимальную программу;
- входной пакет;
- необходимые таблицы;
- параметры сэмплера;
- контекст;
- ожидаемые биты;
- фактические биты.

# 15. Тестовая инфраструктура

## 15.1. Рекомендуемая структура

```text
tests/
    unit/
    integration/
    differential/
    golden/
    concurrency/
    memory/
    compatibility/
    benchmark/
    platform/
```

Каждая категория отвечает за отдельный класс рисков.

## 15.2. Unit Tests

Проверяют:

- арифметические операции;
- отдельные ядра;
- таблицы констант;
- стек VM;
- интерполяцию;
- кэши;
- преобразования типов;
- обработчики.

## 15.3. Differential Tests

Сравнивают Java и C на одинаковых входных данных.

Это основной инструмент проверки численной корректности.

Тесты должны поддерживать воспроизводимые входы и сохранение несовпадений.

## 15.4. Compiler Tests

Проверяют:

- обход графа;
- распознавание типов узлов;
- повторное использование общих объектов;
- генерацию инструкций;
- таблицы констант;
- подписи;
- оптимизации;
- Java fallback;
- стабильность программ.

## 15.5. Program Verifier Tests

Проверяют отклонение:

- неизвестных opcode;
- неправильных индексов;
- переполнений;
- слишком глубокого стека;
- повреждённых таблиц;
- некорректных callback;
- чрезмерно больших программ;
- неправильных заголовков;
- некорректных ссылок;
- недопустимых переходов, если они предусмотрены форматом.

Проверки должны подтверждать не только отказ, но и отсутствие обращения к недопустимой памяти.

## 15.6. Integration Tests

Проверяют:

- загрузку мира;
- обнаружение измерений;
- получение деревьев плотности;
- подключение к noise filling;
- генерацию чанков;
- работу с датапаками;
- Java fallback;
- отключение при несовпадении.

## 15.7. Concurrency Tests

Проверяют:

- одновременный доступ к одной неизменяемой программе;
- разные рабочие контексты;
- независимость рабочих буферов;
- повторное использование памяти;
- освобождение ресурсов;
- отсутствие гонок;
- корректное отключение компонента при одновременном выполнении задач.

Нужно отдельно проверять, что состояние одного мира не попадает в вычисления другого мира.

## 15.8. Memory Tests

Используются:

- AddressSanitizer;
- UndefinedBehaviorSanitizer;
- доступные инструменты анализа памяти;
- тесты граничных размеров;
- тесты неправильных указателей;
- тесты жизненного цикла буферов;
- тесты переполнения размеров;
- тесты некорректных входных программ.

Санитайзеры используются в специальных тестовых сборках.

Их успешное прохождение не заменяет обычные тесты и проверку ABI.

## 15.9. Golden Tests

Golden Tests должны выполняться при каждом существенном изменении:

- компилятора;
- обработчиков;
- оптимизатора;
- нативной VM;
- вычислительных ядер;
- интерполяции;
- кэширования;
- интеграции Minecraft.

## 15.10. Regression Tests

Каждое воспроизведённое несовпадение превращается в постоянный регрессионный тест.

В тестовый корпус добавляются не только ошибочные координаты, но и минимальный контекст, необходимый для повторения ошибки.

Исправление считается неполным, если первоначальный сценарий воспроизведения не проверен повторно.

# 16. Проверка совместимости

## 16.1. Minecraft

Для каждой поддерживаемой версии необходимо проверять:

- получение Noise Router;
- доступность типов узлов;
- поведение обработчиков;
- точку подключения к noise filling;
- интерполяцию;
- кэширование;
- корректность генерации.

Нельзя переносить результаты одной версии Minecraft на другую без соответствующих тестов.

## 16.2. Загрузчики

Каждый адаптер загрузчика должен проверяться отдельно.

Ядро не должно зависеть от конкретного API загрузчика.

## 16.3. Другие моды

Проверяются:

- наличие сторонних обработчиков;
- конфликты компиляции;
- изменения дерева плотности;
- пользовательские функции;
- взаимодействие с другими оптимизаторами генерации;
- корректный Java-only режим при конфликте.

Неподдерживаемая интеграция не должна приводить к изменению результата генерации.

## 16.4. Платформы

Обязательные целевые платформы из архитектурного плана:

| ОС | Архитектура | Проверки |
|---|---|---|
| Windows | x86-64 | Unit, differential, ABI |
| Linux | x86-64 | Unit, differential, ABI |
| Android | ARM64 | Native load, ABI, tests |
| Linux | x86-64, sanitizer build | Memory tests |

Дополнительные платформы не считаются поддерживаемыми до появления соответствующих проверенных сборок.

# 17. Проверка производительности

## 17.1. Отделение от корректности

Бенчмарки не являются доказательством корректности.

Сначала выполняются обязательные проверки, затем измеряется производительность.

Вариант с несовпадениями не может быть выбран независимо от его скорости.

## 17.2. Измеряемые показатели

Рекомендуется собирать:

- время Java reference;
- время нативного исполнения;
- время callback;
- время подготовки пакета;
- время интерполяции;
- время обработки кэшей;
- количество вычисленных точек;
- количество callback;
- размер пакета;
- долю Java fallback;
- пропускную способность;
- общую стоимость генерации.

## 17.3. Воспроизводимость бенчмарков

Необходимо фиксировать:

- модель CPU;
- ОС;
- версию компилятора;
- версию нативного движка;
- конфигурацию сборки;
- используемый вариант ядра;
- тестовый набор;
- количество повторений;
- условия нагрузки.

При интерпретации результатов следует учитывать прогрев, состояние процессора и thermal throttling.

## 17.4. Выбор ядра

Алгоритм:

1. Определить доступные варианты.
2. Проверить требования CPU.
3. Запустить тесты корректности.
4. Исключить некорректные варианты.
5. Измерить оставшиеся варианты.
6. Выбрать самый быстрый корректный вариант.
7. Сохранить сведения о выборе.

Производительность не должна влиять на критерии битового соответствия.

# 19. Обработка ошибок и отказоустойчивость

## 19.1. Ошибки исполнения

Нативный движок должен возвращать структурированные статусы.

Примеры категорий:

```text
SUCCESS
INVALID_PROGRAM
INVALID_OPCODE
INVALID_OPERAND
STACK_ERROR
BUFFER_ERROR
CALLBACK_REQUIRED
CALLBACK_ERROR
UNSUPPORTED_OPERATION
NUMERICAL_MISMATCH
INTERNAL_ERROR
```

Это рекомендуемый набор категорий, который должен быть согласован с фактическим ABI.

## 19.2. Запрет фиктивного успеха

Запрещается:

- возвращать нулевой результат вместо ошибки;
- игнорировать неверные индексы;
- продолжать выполнение после повреждения состояния;
- использовать частично заполненный выходной буфер;
- подавлять диагностическую информацию;
- маскировать ошибку общим успешным статусом.

## 19.3. Java fallback

При ошибке, которую можно безопасно обработать на Java:

- прекращается использование некорректного нативного результата;
- вычисление передаётся Java;
- сохраняется причина перехода;
- при необходимости отключается соответствующий компонент.

Java fallback не гарантирует восстановления после аварии самого нативного процесса, например segmentation fault. Поэтому основная защита должна предотвращать передачу некорректных программ и данных в нативный движок.

## 19.4. Повреждение памяти

При обнаружении признаков нарушения памяти нельзя продолжать использовать потенциально повреждённое состояние.

В зависимости от характера ошибки необходимо отключить соответствующий уровень ускорителя и прекратить опасное исполнение.

# 23. Заключительное правило

Верификация — это механизм допуска, а не формальная процедура ради отчёта.

Каждый нативный компонент должен иметь подтверждённую корректность в пределах заявленной области применения.

Если отдельное ядро не проходит тесты, оно отключается.

Если отдельное поддерево некорректно, используется Java fallback.

Если целое дерево не проходит проверку, оно не допускается к нативному исполнению.

Если безопасность нативного движка не может быть подтверждена, ускоритель отключается.

Нельзя заменять отсутствующие доказательства предположениями о математической эквивалентности, успешной компиляции или высокой производительности.

**Единственный допустимый результат работы Native Noise Accelerator — ускорение, которое сохраняет поведение настоящей Java-генерации Minecraft.**
