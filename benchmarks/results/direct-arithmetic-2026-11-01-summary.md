# Direct C vs Java JIT — сводка трёх независимых JVM

Дата: 2026-11-01

## Условия

- CPU: Intel Xeon E3-1230 v5 @ 3.40 GHz.
- OS: Windows 10 x64.
- JDK: Oracle JDK 25.0.4.1.
- C compiler: MSVC 14.51, Release `/O2 /Ob2 /DNDEBUG /fp:strict`.
- Три независимых JVM fork.
- Одна формула из 36 операций, одинаковые входные данные.
- Один FFM downcall на пакет для native-вариантов.
- Размеры: 256, 4096, 32768, 65536 точек.

## Метод агрегации

Для каждого размера и реализации взята медиана трёх fork-медиан. Диапазон — минимум и максимум этих fork-медиан. Это не доверительный интервал и не диапазон всех измерительных выборок. Единица измерения — ns/point.

## Отношение производительности

Во сколько раз C медленнее Java JIT:

| Размер | C + copies / Java | C prepared / Java |
|---:|---:|---:|
| 256 | 9.17x | 9.09x |
| 4096 | 13.48x | 13.19x |
| 32768 | 12.93x | 11.98x |
| 65536 | 14.62x | 13.94x |

Медиана четырёх отношений для prepared C: **12.58x**.

В этом тесте Java JIT выполняет пакетную арифметику примерно в 9–14 раз быстрее прямого C-вызова.

## Влияние копирования

Устранение копирования входов и выхода из измеряемого участка улучшило Direct C:

| Размер | Снижение ns/point относительно C + copies |
|---:|---:|
| 256 | 0.93% |
| 4096 | 2.20% |
| 32768 | 7.39% |
| 65536 | 4.63% |

Копирование не объясняет основную разницу. Prepared C всё ещё включает FFM downcall и проверку status; это не измерение изолированного машинного цикла без interop.

## Сравнение с scalar native VM

Прямая C-реализация быстрее существующей scalar native VM примерно в 2.43–2.68 раза. Устранение интерпретации помогает относительно текущей scalar VM, однако специализированный Java JIT остаётся существенно быстрее обоих native-вариантов.

## Корректность

Все три fork завершились с exit code 0. Для всех четырёх размеров прошли initial, post-warmup и post-measurement raw-bit gates. Сравнение выполнялось через `Double.doubleToRawLongBits`.

Набор включает конечные значения, signed zero и subnormal cases. Он не доказывает универсальное совпадение NaN payload semantics.

## Интерпретация и решение

Эксперимент показывает, что сам факт использования native C не гарантирует преимущества над JIT. Результат относится к данной реализации, компилятору, CPU и способу interop. Java JIT оптимизирует специализированный цикл; C собран MSVC Release со строгой floating-point семантикой. Использован один FFM downcall на пакет. Буферы подготовлены заранее в отдельном варианте. Измерения warm-cache.

Эксперимент не сравнивает SIMD/SoA C kernel, будущую tile/SoA VM, реальные Minecraft density trees или полный world-generation pipeline.

Практические выводы:
1. Не переносить арифметику в C только ради предполагаемого преимущества native-кода.
2. Не считать текущую scalar VM эталоном будущей tile VM.
3. Сначала реализовать полноценное tile/SoA исполнение и сравнить его с Java JIT.
4. При дальнейшем сравнении C исследовать generated assembly и SIMD-векторизацию.
5. Сохранить raw-bit verification как обязательный критерий допуска.
